## Findings

### P02-T01-R01 — P1: Loading is keyed on an identifier that does not determine the content

Location: [adapter.py](../../pob2-optimizer/pob2opt/evaluation/adapter.py),
`primitives`, line 415; the key written at line 390.

`primitives()` skips the load when `self._loaded_build_hash == document.build_hash`.
`build_hash` is a caller-supplied identifier, not a content hash of the document,
and `document=` is a public parameter. Two different documents carrying the same
`build_hash` therefore produce one load and two identical answers.

Probe 1: a document with `Adds 60 to 90 Physical Damage` and a document with
`120 to 180`, both under `build_hash "probe-build"`, both evaluated through
`adapter.primitives(..., document=...)`. Both returned
`TotalDPS = 47.222385956304`. The second document was never sent to the engine
and nothing reported that.

The same short-circuit also ignores the requested `EngineState`. Probe 2:
applying `{"enemyIsBoss": "Boss"}` changed 56 output keys; the next call with
`EngineState()` and no configuration returned the *same* 56 changed values,
because `set_config` writes into `build.configTab.input` and nothing ever
restores it. An evaluation's result depends on which evaluation happened before
it. That is the defect P07 would inherit and the one hardest to notice later.

Impact: silent wrong results on the production evaluation path. Any cache built
on `EvaluationResult` would store them. This invalidates the A-B-A claim as
written, because A-B-A cannot test state leakage when B is never loaded.

Required change: key the "already loaded" decision on what actually determines
the engine's state — the document's content and the state applied to it — not on
a caller-chosen identifier. Reload whenever the document content or the
requested `EngineState` differs from what is currently applied. Repeating an
identical request may still skip the reload. `create_blank_build` must clear
both keys.

Acceptance: two documents sharing one `build_hash` and differing in a damage
modifier produce different values. `EngineState(config=…)` followed by
`EngineState()` returns the first call's unconfigured values exactly, within the
task's tolerance. Repeating one identical request still performs no reload, and a
test asserts that (otherwise the fix is unobservable). All three cases run
against the real engine, not a synthetic worker, because the leak lives in PoB's
configuration table.

### P02-T01-R02 — P1: The A-B-A evidence never reads B

Locations: [test_p02_t01_engine_adapter.py](../../tests/engine/test_p02_t01_engine_adapter.py),
lines 188-208; [p02_t01_evidence.py](../../scripts/p02_t01_evidence.py),
`pob_section`, the `aba` block.

The test loads A, reads it, loads B, reads A again, loads B, loads A, reads A,
and compares the two A readings. B's values are never read. The only assertion
about B is `stronger != populated_xml`, which compares two Python strings and
says nothing about the engine. The evidence file repeats the shape: `pob.aba`
records a comparison of two A readings and a prose note that B is "the same build
with a stronger fixture weapon".

The P00 test this replaced did better: `test_aba_weapon_swap_returns_identical_stats`
asserts `state_b["TotalDPS"] > state_a1["TotalDPS"]` with the comment "B must
differ, or A-B-A proves nothing". That guard was dropped in the migration.

Impact: the headline acceptance criterion is reported as passing on evidence that
cannot distinguish a working A-B-A from an adapter that ignores every load after
the first. Probe 1 shows that is not hypothetical.

Required change: read B and assert it differs from A on a named primitive before
comparing A to A. Record B's value in the evidence file. Do the same in
`scripts/p02_t01_evidence.py` so the artifact carries the same proof.

Acceptance: the engine test fails if the adapter ignores the B load.
`lifecycle.json` → `pob.aba` contains A's, B's and A's second reading for a named
key, and a `b_differs` boolean. Mutating the adapter to always skip reloading
must fail the test.

### P02-T01-R03 — P2: A caller's defect is reported as invalid input

Location: [documents.py](../../pob2-optimizer/pob2opt/evaluation/documents.py),
lines 37-42.

`except Exception` around `self.blobs.get(blob_hash)` converts every failure into
`EngineInvalidInput`. Probe 5 passed a store whose `get` raises `TypeError` and
received `invalid_input: "raw document blob … is unavailable: a defect in the
caller, not a bad document"`. A missing blob, a corrupt blob, a disk error and a
programming mistake are four different things, and `invalid_input` means "the
build was not describable", which is true of only one of them.

Required change: catch the P01 storage errors (`BlobNotFound`, `BlobCorrupt`) and
`OSError` as `invalid_input`; let anything else surface as `internal_error`.

Acceptance: a missing blob and a corrupt blob give `invalid_input`; a store that
raises `TypeError` gives `internal_error` and a diagnostic that does not claim the
document was unavailable.

### P02-T01-R04 — P2: The build document is chosen by list position

Location: [documents.py](../../pob2-optimizer/pob2opt/evaluation/documents.py),
line 36.

`build.raw_blob_hashes[0]` is an undeclared interpretation. `BuildSpec` permits
several raw blobs and the contracts do not say the first is the PoB document;
P04 has not defined the ordering. Probe 4 stored two valid-looking documents and
got the first with no indication a choice was made.

Required change: with exactly one raw blob, use it. With more than one, refuse
with `invalid_input` naming the ambiguity, unless the caller selects one
explicitly. Do not guess which blob is the build document before P04 defines it.

Acceptance: one blob loads; two blobs raise `invalid_input` naming both hashes;
an explicit selection of either hash loads that one; selecting a hash the build
does not reference is refused.

### P02-T01-R05 — P2: The checkout identity can be stale for the life of the process

Location: [checkout.py](../../pob2-optimizer/pob2opt/evaluation/checkout.py),
`_CACHE` at line 37 and `resolve_checkout`.

A module-level cache keyed only by path, never invalidated. Probe 6 resolved a
clean checkout, created a file in it, resolved again and still got
`dirty_hash: None`; `use_cache=False` reported the modification. A long run that
has already resolved a checkout will keep asserting it is pinned after someone
edits it, and the identity recorded on every snapshot will be wrong. The cache
is also shared global state between tests.

Required change: remove the process-wide cache. `EngineAdapter` already resolves
once and keeps the result on the instance, which is the correct scope, and one
`git` call per adapter is not worth a correctness hazard.

Acceptance: resolving the same checkout twice across a modification reports the
modification the second time. No module-level mutable cache remains.

### P02-T01-R06 — P2: Helper Lua is injected into every engine and named in no identity

Locations: [protocol.py](../../pob2-optimizer/pob2opt/evaluation/protocol.py),
`EngineIdentity`; [adapter.py](../../pob2-optimizer/pob2opt/evaluation/adapter.py),
`identity`.

`opt_helpers.lua` and `tree_lib.lua` are loaded into the Lua state on every exact
load and every blank build, so they are part of what produced a value. The
identity records the PoB commit, the dirty hash and `adapter_version`, but
editing a helper changes results while leaving every identity field unchanged.
P00 recorded `helper_lua_sha256` in its measurements for exactly this reason;
the adapter dropped it. `architecture.md` puts "adapter version" in the cache
key, and a hand-maintained version string is not a substitute for a hash of the
code that ran.

Required change: resolve the helper files' SHA-256 in the parent, before the
spawn, and carry them on `EngineIdentity`.

Acceptance: two adapters pointed at helper files differing by one byte produce
different identities. The hashes appear in `lifecycle.json`.

### P02-T01-R07 — P3: A moved working directory can hide the failure that mattered

Location: [adapter.py](../../pob2-optimizer/pob2opt/evaluation/adapter.py),
`_request`, the `finally` calling `_assert_parent_cwd`.

Raising inside `finally` discards the exception in flight. If a request times out
*and* something moved the parent's directory, the caller sees only
`internal_error: the coordinator working directory moved`, and the `timeout` is
demoted to `__context__`. The diagnostic that explains why a build has no result
is the one that gets lost.

Required change: check the directory on the success path, and on the failure path
attach it to the typed error rather than replacing it.

Acceptance: a request that times out while the directory has moved reports
`timeout` with the directory change named in the diagnostic.

### P02-T01-R08 — P3: The reported bound is not the bound that applied

Location: [adapter.py](../../pob2-optimizer/pob2opt/evaluation/adapter.py),
`primitives`, lines 412-432.

`PrimitiveSnapshot.timeout_s` carries the fidelity-selected bound for the
primitives request, but the exact load inside the same call always uses
`detailed_timeout_s`. At screen fidelity the snapshot says 30 s for an operation
that was allowed 330 s. `duration_ms` likewise covers both.

Required change: record both bounds.

Acceptance: a screen-fidelity snapshot after a load reports the primitives bound
and the load bound separately, and the worklog states that `duration_ms` spans
both.

### P02-T01-R09 — P3: `except … : pass` on the worker's send path

Location: [worker.py](../../pob2-optimizer/pob2opt/evaluation/worker.py), `_send`.

`architecture.md` says never use `except: pass` in a production boundary.
`_close_quietly` carries a comment explaining why its swallow is correct; `_send`
does not. The swallow is probably right — a broken pipe means the parent is gone
and there is nowhere to report — but the rule exists so that judgement is written
down and reviewable.

Required change: name the condition and say why nothing can be reported, or
report to stderr.

Acceptance: no unexplained `pass` handler remains in the package.

### P02-T01-R10 — P1: A replaced worker answers for a build it never received

Location: [adapter.py](../../pob2-optimizer/pob2opt/evaluation/adapter.py),
`primitives`, the reload decision; `_request`, which cleared the tracked load
only for `EngineTimeout` and `EngineCrash`.

The parent recorded *which* build was loaded but not *where*. The reload
decision is taken before any request is sent, so it reads state belonging to a
worker that may already be dead. After a fatal failure — a malformed document,
say — the handle is discarded, the next `primitives()` call sees a matching
load key, skips the load, and only then does `_ensure_worker` start a fresh
process. That process holds PoB's default build.

Reproduced at HEAD, after the R01 repair: a build with 36 allocated nodes and
one item, a rejected malformed document, then the same evaluation returned
`"Unnamed build"`, level 1, 1 allocated node, 0 items, with
`document.reloaded: false` and the requested build's hash on the snapshot. The
numbers were a blank level 1 character's.

Impact: the same class as R01 and at least as severe, because it happens on
the recovery path the task's own acceptance criterion exercises. "A fresh
worker finishes a subsequent task" was satisfied by a worker that finished the
wrong task.

Required change: scope the tracked load to the worker generation that
performed it, and clear it whenever the handle dies for any reason, not only
on timeout and crash. A load must be skipped only when the process that did
the loading is still the one serving.

Acceptance: an evaluation after a rejected document reloads and returns the
original build's values, matching the pre-failure reading within tolerance.
The same holds after `restart_worker()` and after an external kill. Each case
asserts `document.reloaded is True`, so a regression is visible without
comparing 675 numbers.

### P02-T01-R11 — P2: The fidelity bound is not a bound on the operation

Location: [adapter.py](../../pob2-optimizer/pob2opt/evaluation/adapter.py),
`primitives` and `load_exact_build`.

`primitives(fidelity=SCREEN)` applied the 30-second screen bound to the
primitives request only; the load inside the same call always used the
detailed bound. `interfaces.md` declares "30 seconds per screen" for an engine
evaluation, and an evaluation includes getting the build into the engine.

Reproduced at HEAD with a worker that sleeps one second in `load_exact_build`
and a screen bound of 0.1 s: the call **succeeded** after 1.219 s, reporting
`timeout_s: 0.1` and `load_timeout_s: 300`. A caller who set a bound did not
get one.

This subsumes the P3 reporting issue I originally filed as R08: the bound was
not merely mis-reported, it was not applied.

Required change: the load performed inside an evaluation uses that
evaluation's bound. A direct `load_exact_build()` call keeps the detailed
bound.

Acceptance: a screen-fidelity evaluation whose load exceeds the screen bound
raises `timeout` with stage `load_exact_build`. A detailed evaluation with the
same slow load succeeds and reports both bounds.

### Concerns, not defects

- Nothing cross-checks the loaded character against the `BuildSpec` (probe 3).
  Doing so needs a catalog mapping from `class_id` to PoB's class name, which is
  P02-T02. The right action now is to record what was and was not verified on the
  snapshot, and to open the check as P02-T02 work rather than implying it exists.
- `_check_profile` compares `pob_commit` only, not `profile.adapter_version`
  against `ADAPTER_VERSION`. A profile pinned to another adapter is accepted.
  P02-T02 owns the profile; flag it there.
- A worker that cannot start is respawned on every subsequent request, so a
  permanently broken configuration pays a full boot per call. Bounded retry
  belongs with P08's coordinator.

## Reassessment

- Assumptions confirmed: one engine per process with coordinator-side bounds is
  workable, and the existing cwd-changing engine is usable unchanged inside a
  worker. A cold boot costs ~1.5 s, so reloading per evaluation is affordable.
- Assumptions contradicted: that "the build is already loaded" is a safe
  optimization. It is not, while engine configuration persists in the Lua state
  and the key is a caller-supplied identifier.
- Contracts to revise: none. `EngineIdentity` gains helper hashes, which is an
  addition, not a change to an accepted contract.
- Prior gates invalidated: none. G0 is unaffected; G1 was never claimed.
- Required revalidation: the engine lane and `lifecycle.json` must be regenerated
  after R01 and R02, because every recorded value was produced by the defective
  path.
- Next task: P02-T02 after these repairs, as planned.
- Owner decision needed: none.

### A defect introduced by the R06 repair, and caught

Hashing the helper files as raw bytes made the engine identity depend on how
git checked them out: `tree_lib.lua` hashed to `836bfd9c…` on this CRLF
checkout against the `d6b30d7d…` P00 recorded for the same unmodified file.
Two machines running identical code would have produced different identities
and split any cache built on them. The worker reads these files as text, so
the hash is now taken after newline translation, which is what the engine
actually receives. Both helpers now match P00's recorded values exactly, and
`test_the_helper_hash_matches_the_value_p00_recorded` pins that agreement.

### Disposition after repair

The eleven findings are closed. What this verification is *not*: an
independent acceptance. I wrote the implementation, the review and the
