## Findings and repair acceptance

### R1 — P1 — Coverage reads the first sets instead of the active loadout (#19)

Locations: `pob2-optimizer/pob2opt/coverage/inputs.py:104`, `:116`, `:121`, `:129`.

`build_facts_from_pob_xml` uses the first SkillSet, tree Spec, ItemSet and ConfigSet. A document selecting set/spec 2 is analysed using set/spec 1. The independent probe puts an unknown skill and an enabled condition in active set 2: coverage facts instead contain the known inactive skill, passive 1, item 1 and empty config. PoB's SkillsTab and ConfigTab load their declared active IDs; P04 already has loadout selection semantics.

Impact: coverage can approve different skills, gear, passives and conditions from those PoB evaluates. Multi-loadout imports are already supported upstream; this is not a hypothetical future format.

Repair: use the established loadout/linking rules and require the same selected variant for facts, native capture and scoring. Report missing/ambiguous linked sets as blocking gaps. Do not silently choose the first element.

Acceptance: a two-loadout document with unsupported state only in the selected second loadout must block; selecting the supported first loadout must analyse that loadout. Check all four set types and non-consecutive IDs against PoB's selected identity.

### R2 — P1 — Missing and stale parse evidence can pass coverage (#19)

Locations: `coverage/analysis.py:403` (missing passive defaults to an empty list), `:438` (items keyed only by slot), `:459` (captured config replaces candidate config); `coverage/inputs.py:161` (`ModSupport`). Paths are under `pob2-optimizer/pob2opt/`.

Independent probes all return `eligible=true` with no blocking findings:

- Allocate passive `99999999` with an empty node parse report.
- Change the equipped Ring 1 item and supply a report for the slot with an explicitly wrong PoB commit.
- Enable a candidate condition while supplying an old empty captured config list.

The report format does not bind parse verdicts to the candidate document/effective state. Its PoB commit is not checked. Missing passive entries disappear through `.get(node, ())`. In #21, defaulting to the committed seed report makes this particularly dangerous for another candidate.

Repair: bind evidence to the selected/scored document hash, engine identity and effective state; verify the binding before consuming any verdict. Require complete coverage of allocated nodes and equipped item identities/text, and distinguish a verified empty line set from an absent entry. A registry rule may explicitly cover a known node, but an unregistered absent node cannot pass. Reconcile config evidence with the exact document and calculation overrides.

Acceptance: all three probes must produce typed blocking gaps; a correctly bound, complete capture must still pass. Replacing an item with a different item in the same slot, adding a passive, changing config or changing the engine must invalidate affected coverage.

### R3 — P1 — The enemy-prefix shortcut treats derived state as fixed target data (#19)

Locations: `pob2-optimizer/pob2opt/coverage/analysis.py:76` and `:501`.

The `TARGET_VAR` regex exempts essentially every `enemyX` setting without comparing its value with the scenario. The probe supplies `enemyCriticalWeaknessStacks=20` and receives an eligible decision without a rule deriving those stacks. This is a real pinned PoB option (`src/Modules/ConfigOptions.lua:1911`), not an invented variable. It represents a debuff magnitude, not a fixed Pinnacle target property. Even genuine target settings are accepted without checking their prescribed values.

Repair: replace the prefix exemption with explicit, value-checked bindings to scenario-owned fields. Conditions, stacks and other build-generated state require their own coverage rules and evidence. Do not broaden the D07 charge/Hit and Run method amendment to other conditions.

Acceptance: unproven Critical Weakness stack count and mismatched enemy level/armour must block; exact approved target values must pass; a separately supported debuff rule must validate its magnitude/uptime.

### R4 — P1 — The attribution table actually scored is not the table approved by coverage (#21)

Locations: `pob2-optimizer/pob2opt/combat/flicker.py:140` and `:213`; `combat/resolutions.py:194`.

Coverage receives hardcoded skill-owner assignments, while the timeline receives the caller's independent `AttributionTable`. There is no binding between them or the acceptance's table ID. With the existing settled fixture, an unaccepted table assigning Whirling Assault hits to `flicker_secondary` returns **eligible**, scoring **525,000,000,124.1667** instead of **124.1667** when Whirling damage is set to 1e12 per use. This bypasses the retained D07 attribution gate.

Repair: approve and persist one exact version/hash of the complete table, and use that same content for coverage and scoring. Missing, changed or contradictory assignments must block. A supplied acceptance for table A cannot approve table B.

Acceptance: rerun the adversarial table probe with both a previously settled registry and an explicit acceptance for a different table. Both must refuse an objective. Increasing unrelated damage must leave a legitimately eligible Flicker objective unchanged.

### R5 — P1 — Evaluator assumes clean pinned provenance instead of checking captured values (#21)

Locations: `pob2-optimizer/pob2opt/combat/flicker.py:99` and `:120`; `combat/values.py:64` and `:245`.

`evaluate_flicker` constructs coverage's engine state from default `PIN, False`, independent of `CycleValues.engine`. Values explicitly declaring `head='wrong-commit', dirty_hash='dirty'` still produce an eligible score in the settled fixture. Values also carry no checked hash binding to the scored XML; the string `document='benchmark'` does not establish that they belong to this candidate.

Repair: obtain engine/document/state identity from the capture, preserve it through frozen replay, and verify it against the requested scored document and profile. Missing provenance must remain unknown unless running an explicitly diagnostic synthetic lane. Caller defaults must not manufacture a clean-engine assertion or override contradictory capture metadata.

Acceptance: wrong commit, dirty engine, absent identity and values from another document each block objective production. Live and frozen captures of the exact same scored document should agree and remain reproducible across fresh workers.

### R6 — P1 — Different scoring windows share one objective and evaluation identity (#21)

Locations: `pob2-optimizer/pob2opt/combat/flicker.py:103`, `:213`, `:249`.

The public evaluator accepts arbitrary `window_s`/`burst_s` but always emits the fixed v1 objective. The evaluation hash omits both windows. Independent runs at 120 s and 12 s return **eligible** with the exact same evaluation ID but scores **124.1667** and **120.8333**. Changing the burst window also retains the ID. The hash additionally omits the scenario content and relevant coverage/gating inputs.

Repair: enforce the fixed 120 s / 5 s v1 contract for eligible objective results. Alternative windows may be separately identified diagnostics or separately versioned objectives. Include all result-affecting scenario, method, engine/profile and evidence identities in evaluation identity; preserve worker-PID independence.

Acceptance: alternate windows cannot enter the v1 ranking; changed scenario or eligibility evidence cannot reuse a result/cache identity. Identical semantic inputs in fresh workers still produce the same identity.

### R7 — P2 — An unsupported method name runs the community-method simulator (#21)

Locations: `pob2-optimizer/pob2opt/combat/resolutions.py:152`; `combat/flicker.py:213`.

`apply_method` returns for a non-community method, but the evaluator still runs the same charge-assuming timeline. Once unrelated registry gaps are settled, asking for `pob-cycle-v1` returns an eligible result identical to `pob-community-v2`, merely relabelled. The former method is explicitly distinct and still blocked in the protocol.

Repair: validate supported methods at the evaluator boundary. Until another method has its own implementation and prerequisites, return a typed unsupported-method result with null objectives. Do not rely on incidental unsettled registry entries to prevent execution.

Acceptance: `pob-cycle-v1` and an unknown method ID remain blocked even with a completely settled registry. `pob-community-v2` retains its explicit method assumptions.

### R8 — P2 — Slot uncertainty is recorded but lost by legality and pool consumers (#22)

Locations: `pob2-optimizer/pob2opt/catalog/rules.py:491`, `:581`; `evaluation/legality/checks.py:645` and `:661`.

The independent probe extends the PR's own mixed-rarity test through real legality validation. Remove unique Bow acceptance from Weapon 1's probe while keeping other unique categories: export correctly emits blocking `slot-rarity-partial`, but a unique Adherent Bow receives `CHECK_SLOTS=legal`, and the report does not cite that gap. Making Bow acceptance partial instead yields `illegal`, even though the category-level information cannot decide that individual base. Both collapse an explicitly unknown rule into a definite answer.

Repair: carry slot/category/rarity uncertainty into the executable rules and consumers. Return unknown for affected combinations; retain definite answers for unaffected combinations. Apply the same treatment to partial/missing off-hand contexts and probe failures. A global descriptive gap which consumers ignore is insufficient.

Acceptance: extend mixed-category and mixed-rarity tests to check legality, pool eligibility/provenance and the cited gap. The affected combination must be unknown, never silently legal or definitively illegal from incomplete evidence. Re-run the native slot matrix to preserve known positive/negative cases.
