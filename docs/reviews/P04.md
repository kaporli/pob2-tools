## Findings

### R1 — P1: Generated groups can contain user-added supports that are silently discarded

Locations: `evaluation/builddoc.py:885` (`_import_skills`, especially the `source` filter); `evaluation/importaudit.py:138` (`_audit_generated`); `evaluation/builddoc.py:1000` (the generated-only main-group exception).

Every group with `source` is omitted from BuildSpec. The audit checks selected attributes but never checks whether a generated group contains additional support gems. Upstream rebuilds the granted active skill, but preserves the user's additional gems on an existing generated group; rebuilding the group from gear/tree alone does not recover those supports.

Reproduction: start from b09's generated Spear Stab, remove the ordinary authored group, attach the existing b12 `SupportAddedColdDamagePlayer` gem, select the first group, then have pinned PoB save the document. Parsing that saved document reports **complete**, no issues, and a **recommended** export. The support is absent from the export. Pinned PoB evaluates the same main skill on each side, but **TotalDPS changes from 24.573328 to 16.935672**. Multiple other stats change too. Both XML documents are retained.

Required repair: either represent and faithfully restore user state attached to generated groups, or mark every unrepresented added gem/setting as a blocking loss before omitting that group. A generated-only main group is safe only after its regenerated state has been established as equivalent. Do not turn the finding into a non-blocking note.

Acceptance: use the retained source XML as an adversarial fixture. Its supported export must retain the support and match PoB, or the build must be partial and non-recommendable. Test supported defaults separately from generated groups with added enabled/disabled supports, multiple added gems and changed user settings. Assert that a support with all default attributes is still detected as user content.

### R2 — P1: Gameplay-relevant parser issues do not taint the persisted build or items

Locations: `parsers/pob.py:237`–280; `_finish_build` at 316; `_modifier_checks` at 391.

Builds are finalized and appended before item-affix and template-readiness checks. Those checks only add ParseResult issues; they leave the affected ItemInstance and BuildSpec complete. Two independent cases reproduce the leak: append an unknown affix to an equipped rare, or reduce that rare to its rarity/name/base lines. The result is partial with `unresolved_affix` or `template_claim`, but **the build and items remain complete, and `export_build` recommends the export**.

A consumer loading the stored BuildSpec/ItemInstance does not have to retrieve the ParseResult to discover these blockers. This repeats the class of defect guarded against in PR #5. Keeping modifier IDs out of exported item text does not require discarding readiness failures.

Required repair: propagate gameplay-relevant resolution/readiness failures to the affected item and every variant using it, with precise unresolved references. Preserve unknown text. Keep harmless metadata and unrelated unlinked sets non-blocking for otherwise complete variants. Do not solve this by blindly making every variant partial whenever the document has any issue.

Acceptance: exercise unknown and ambiguous affixes, out-of-range rolls and name-only equipped items through the public parser and stored corpus. Retrieve builds/items without their ParseResult and verify they remain non-recommendable. Include one unaffected variant and a harmless metadata note as controls.

### R3 — P2: Parse caching ignores the catalog and interpretation options

Locations: `parsers/cli.py:96`–102; `parsers/pob.py:98` (`_result`); source-derived output IDs in `parse_pob_xml` and `split_variants`.

The stored result ID is only source ID plus parser version. Parsing the same source with catalog A and then catalog B returns the old result immediately, even though B was explicitly supplied. The probe uses two actual catalog-export bundles; B removes the granted-skill rows. The second CLI call returns exit 0, `unchanged: true`, `status: complete`, and a build still bound to A. A fresh parse under B is partial. `--tree-version` and `--format` are likewise bypassed on a cache hit.

Changing only the ParseResult ID is insufficient: build/item/claim record IDs also need a collision-safe strategy when reinterpreting the source. Immutable records must not be overwritten or collide. The cached branch also always exits 0, even for a stored invalid/unsupported result whose first parse exits 3.

Required repair: define a versioned parse-context identity including the source, parser/dispatch version, catalog identity and semantic options. Use it consistently for caching and dependent records, reusing only records whose complete contents are actually identical. Preserve prior results and their provenance. Map cached status to the same exit code as a fresh parse.

Acceptance: A→B→A in one corpus returns separate correct interpretations and then reuses A. Changed declared format/tree version is honored; unchanged context is idempotent. Repeat an unsupported parse and keep exit 3 on both calls. Verify stored references after all operations.

### R4 — P2: Cross-patch migration misses support gem identities

Location: `parsers/resolve.py:239`–272 (`_references`).

The reference walker checks `SkillEntry.gem_id` and `support_ids`, but never the new `SkillEntry.supports[*].gem_id`. Removing `Metadata/Items/Gems/SkillGemAbidingHexSupport` from the target gem table while retaining its granted effect produces **no reported removals, no unresolved refs, and a complete migrated build** with the missing gem still referenced. The target-catalog declaration therefore overstates what was resolved.

Required repair: enumerate all v2 support gem references, including triggered skill entries, with exact field paths. Review the reference inventory for other schema fields omitted by this migration. A removed native ID stays explicit and partial; it must not be silently substituted by an effect or display name.

Acceptance: remove a support gem while retaining its effect, remove an effect while retaining its gem, and rename a support gem. Check removal/rename reporting, partial status where needed, source immutability and export eligibility against the target catalog.

### R5 — P2: v1→v2 migration changes the evaluated main skill

Locations: `domain/migrate.py:64`–69; legacy branch of `evaluation/builddoc.py:313`–316.

The migration promises to preserve the group the v1 exporter selected, but assumes that means the first group with a main skill index. The actual legacy exporter uses `main_socket_group == 1` as its unset sentinel: after selecting group 1 it can select a later group as well. With two groups whose main skill indices are both set, v1 exports group 2 while the migration explicitly writes group 1.

This is not merely a label difference. On the b03-derived support-free example, pinned PoB changes from **Ball Lightning, TotalDPS 81.75**, to **Armour Breaker, TotalDPS 3.1634592**. Both exports are recommended. The existing migration test covers a fixture that does not expose the sentinel behavior.

Required repair: preserve the actual supported v1 export semantics in the compatibility migration, or explicitly mark an ambiguous historical main selection unknown and require source re-import. Do not silently reinterpret immutable v1 records or claim a faithful migration while changing their evaluated skill.

Acceptance: cover first-group and later-group selections, both first two indices set, only one set, neither set and no groups. Compare the actual v1 and v2 exports, plus PoB main-skill/numeric results for distinct skills; retain v1 hash compatibility.

### R6 — P2: Malformed numeric source fields escape as exceptions

Locations: `parsers/pob.py:162`–207 (only XML syntax is caught before `split_variants`); numeric parsing reached through `evaluation/builddoc.py` and `evaluation/importaudit.py`.

Well-formed XML with `Build@level="not-a-number"`, `Spec@nodes="broken"`, or an active gem's `level="broken"` raises an uncaught ValueError from the public parser. These bytes can pass raw XML acquisition. Instead of an invalid/partial ParseResult naming the bad field, parsing aborts and the CLI cannot provide its documented typed outcome.

Required repair: validate expected scalar types/ranges at the source boundary and report precise ParseIssues. Catch recognized input-conversion failures at an appropriate boundary; do not convert arbitrary programmer/storage exceptions into successful partial parses. Do not default malformed numbers to zero.

Acceptance: exercise malformed build level, passive ID, active/support level/quality, item numeric fields and selectors through both API and CLI, retaining source evidence and actionable locations. Ensure a failing variant does not falsely become a complete empty build.

### R7 — P2: Engine parity assertions ignore zero-to-nonzero changes and added stats

Location: `tests/engine/test_p04_round_trips.py:65`–77 (`_stat_differences`).

When the source value is zero, the helper forces relative error to zero and requires both absolute and relative error to exceed tolerance. Thus `{Damage: 0}` → `{Damage: 1000}` returns no differences. It also iterates only the source keys, so adding a new numeric output is invisible. The green engine suite does not establish the stated "every numeric stat" claim with this comparator.

Required repair: compare the full numeric-key union with explicit missing-key and non-finite-value handling; use a defined absolute/relative tolerance rule that works at zero. Add independent tests of the comparator itself, then rerun the engine suite and refresh its evidence.

Acceptance: zero↔nonzero, added/removed keys, unchanged zero, small absolute error near zero, relative tolerance on nonzero values and non-finite outputs all have explicit expected results. No large zero-origin change may pass.

### R8 — P2: The independent field audit omits the selected main group

Location: `parsers/corpus.py:297`–415 (`audit_variant`).

For b03, changing the normalized main group from 0 to the other valid group 1 and recomputing its hash still yields **passed, zero mismatches**. That changes the evaluated skill, yet the purported independent skills audit does not inspect `main_skill_group` or the group's main index. It also does not compare gem identity/variant alongside the skill ID. Existing agreement percentages cover only the fields actually enumerated, not all required gameplay settings.

Required repair: expand the independently read source projection to cover the new main-group selection, per-group main selection, active/support gem identity and relevant group state. Audit the remaining required fields explicitly; narrow evidence wording wherever a field is not checked. Avoid calling the importer to generate expected values.

Acceptance: corrupt one valid main-group selection, one per-group selection, one support gem/variant identity and one group enabled flag without changing other fields. Each must create a located mismatch. Retain the existing modifier/support-value corruption checks and regenerate the ten-build audit.

## Reassessment and disposition

The remaining defects are demonstrated behavioral failures, not a request to implement blocked providers or the entire optimizer in this PR. The generated-group exclusion is valid only for state PoB actually regenerates. Parser completion must survive the transition from ParseResult to persisted standalone records. Catalog/patch context is a parsing dependency and must participate in cache identity.

Repair this PR before dependent P05/P06 production work consumes its complete records. Independent pool/search/simulator fixture work can continue under the existing synthetic scope. No owner decision is needed to fix these cases.

After repair, bump affected parser/migration interpretation versions as needed, reparse the affected corpus into new immutable records, and invalidate evaluations derived from incorrect complete flags or lost support/main-skill state. Preserve original source evidence. Rerun both offline suites, the corrected full engine suite, stored-context tests and the independent audit. Existing upstream P00/P01/P02 gate decisions are not blanket-revoked; the new P04/support-fidelity acceptance is withheld. No downstream gameplay/live-market gate is granted.
