## Findings

### P01-R01 — P1: Enforce task transitions when committing results

Location: [repositories.py](../../pob2-optimizer/pob2opt/storage/repositories.py), `_close_task`, lines 408–432, especially the unconditional update at 422–426.

`TaskStore.cancel` makes a task terminal, but `commit_evaluation` bypasses that state machine. `_close_task` only treats already-completed tasks specially; it moves every other state to completed. I enqueued and dispatched a task, cancelled it, then delivered its result. The stored state changed from `cancelled` to `completed`, contradicting `TASK_TRANSITIONS` and reviving cancelled work. Queued and failed tasks have the same unchecked completion path.

Required change: check the allowed transition inside the same transaction that writes the evaluation and closes the task. Keep an identical completion retry idempotent, but reject illegal transitions without inserting a new evaluation. Validate the task/result association rather than accepting an arbitrary result solely because a task ID exists. Define the handling of a late result after retry/recovery explicitly; task attempt information must not silently describe the wrong completion.

Acceptance: dispatched/running completion succeeds; an identical completed-task retry is a no-op; a different result for that completed task fails; completion of cancelled, queued or failed tasks is rejected and leaves both task and evaluation tables unchanged. Include a cancellation/late-worker-result test through `RunStore.commit_evaluation`, not only tests of `TaskStore` methods.

### P01-R02 — P1: Make accepted records survive JSON round trips

Locations: [codec.py](../../pob2-optimizer/pob2opt/domain/codec.py), lines 143–149; [validation.py](../../pob2-optimizer/pob2opt/domain/validation.py), the conditional shape pass at lines 216–221.

`from_jsonable` rejects `None` before it checks whether the annotation is `Any`. The schema for a free-form JSON value permits null, and the encoder writes it. Dataclass instances also skip the decoding/shape pass during validation. Consequently, an `ItemInstance` with `properties={..., "unknown_property": None}` passes `validate_record` and `put_normalized`, but `get_normalized` raises `CodecError: /properties/unknown_property: null is not allowed here`. The store has accepted a record it cannot read. This directly breaks the unknown-versus-zero contract and affects extensible JSON fields used by future parsers.

The skipped shape pass also permits malformed dataclass instances to reach semantic code: replacing an EvaluationResult's status with the valid wire string `"ok"` raises a raw `AttributeError` during validation instead of producing a report or a consistently decoded record.

Required change: allow null for `Any` JSON values while retaining rejection for explicitly non-nullable typed fields. Apply equivalent shape/type validation to dictionary and dataclass inputs; annotations alone do not enforce constructor arguments. Ensure semantic checks receive properly typed records and bad data returns a path-bearing validation report.

Acceptance: dictionaries and dataclasses containing null, zero, false and nested null values in free-form fields have consistent validation, encoding, decoding and storage-read behavior. Test a full put/get round trip. Non-nullable fields must still reject null. Incorrect dataclass enum/nested-field types must not escape as `AttributeError` or another unclassified implementation exception.

### P01-R03 — P1: Require a complete reference graph before accepting a run bundle

Locations: [repositories.py](../../pob2-optimizer/pob2opt/storage/repositories.py), `_require_valid` at 478–482 and `validate_stored`; [validation.py](../../pob2-optimizer/pob2opt/domain/validation.py), `_references` at 713–774; [runbundle.py](../../pob2-optimizer/pob2opt/storage/runbundle.py), `copy_references` and `self_check` at 174–204.

The reference validator is optional at storage boundaries, covers only a subset of reference fields, and is not part of bundle readiness. `put_normalized` successfully inserts a build into an otherwise empty corpus. A later `validate_stored` reports seven unresolved paths, including catalog, equipped item, listing, rotation, source and raw payload. Copying only that build into a new bundle produces `self_check(): readable=True`, with zero blobs, zero missing records and zero missing blobs. Its supposedly self-contained snapshot cannot resolve the build's dependencies.

Even an explicitly supplied populated index misses several references. Replacing `PatchProfile.patch_evidence_ids`, `MechanicRule.dependency_ids` or `RunManifest.source_snapshot_ids` with nonexistent IDs still returns `ok=True`. The handoff's claim that every cross-record reference is checked is therefore false. `validate_stored` also iterates only source/normalized tables, not all persisted record kinds.

Required change:

1. Inventory every actual cross-record/blob reference from the contracts and validate it against the appropriate namespace. Treat an explicitly supplied empty index as an empty corpus, not as permission to skip checks. Do not interpret arbitrary display labels as record IDs.
2. Permit acquisition/staging of incomplete data explicitly, but require reference validation before records are accepted as normalized or a snapshot is declared ready. Use a validated batch/transaction where cyclic references require it; do not break valid batch imports by validating each new row against an incomplete pre-insert index.
3. Make bundle creation/copy/finalization verify the transitive dependencies it promises to freeze. Either copy the required graph or report precise missing dependencies and refuse readiness. Check the manifest and all stored result/gap/observation references as applicable, not just the caller's list of copied IDs.
4. Keep raw payload availability separate from a record merely claiming its hash. A corpus record that names a blob is not proof that the bytes are available in the run.

Acceptance: importing/copying a build without its equipment/catalog/rotation/raw payload must fail validation or report an explicitly incomplete snapshot. The three missing-reference cases above must be reported at their field paths. A fully closed fixture graph must remain valid and readable after the original corpus is disconnected; corrupt or omitted dependencies must be detected. These checks should execute through storage/bundle APIs, not only a separately invoked validator that callers can forget.

### P01-R04 — P2: Allow multiple evaluations of one candidate per generation

Location: [migrations.py](../../pob2-optimizer/pob2opt/storage/migrations.py), lines 184–185 (`UNIQUE (run_id, generation_id, candidate_id)`).

That uniqueness constraint makes a candidate equivalent to one evaluation task. I queued a clear-scenario task, then a boss-scenario task using different task IDs for the same candidate and generation. The second enqueue raises `IntegrityError`. The same restriction prevents screening and detailed tasks or multiple evaluation seeds for that candidate. An EvaluationResult represents one scenario/fidelity/seed, and `commit_evaluation` closes the task with one result, so a single candidate task cannot represent the specified collection of evaluations.

Required change: keep task identity unique while allowing distinct evaluation contexts for the same candidate/generation. The candidate/generation index can remain a non-unique grouping index; if semantic deduplication is wanted, use the full immutable evaluation-task identity. Do not invent new candidate IDs for the same build merely to bypass the constraint. Handle the schema change according to the numbered migration/checksum policy instead of silently editing history for databases that have already applied v1.

Acceptance: queue and independently complete clear and boss tasks for one candidate in one generation; also cover screen/detail and different seeds. Recovery preserves all completed evaluations and returns only unfinished tasks to the queue. Repeating the same task identity must still be idempotent. Revise the existing uniqueness test that currently asserts this overly restrictive design.

### P01-R05 — P2: Include constituent evaluation identities in aggregate cache keys

Location: [cache.py](../../pob2-optimizer/pob2opt/domain/cache.py), `AggregateKey` at lines 131–186.

Changing only `RunManifest.rng_seed` changes `EvaluationKey.from_manifest(...).cache_key()` but leaves `AggregateKey.from_manifest(...).cache_key()` unchanged. The aggregate key has no fidelity, seed or collection of constituent evaluation keys/IDs. An aggregate score derived from different simulation outcomes can therefore reuse the old identity. The handoff acknowledges dropping seed/fidelity and argues that AggregateResult cites its evaluations, but those citations are not included in AggregateKey and cannot prevent this collision.

Required change: derive aggregate identity from the complete set of component evaluation identities, together with objective and baseline-suite identity. Preserve scenario/rotation associations where they matter. An equivalent explicitly complete dependency structure is acceptable; do not rely on payload fields that never reach the key.

Acceptance: changing a constituent evaluation's scenario, rotation, fidelity, seed or other evaluation dependency changes aggregate identity. Objective/baseline changes also force a miss. Reordering a semantically unordered set of identical component evaluations must not create a spurious miss. This closes the unapproved deviation from architecture.md's additive aggregate-cache contract.
