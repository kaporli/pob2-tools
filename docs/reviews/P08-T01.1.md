## R1 P2 Validate that the selected identities represent Flicker Strike

Location: `pob2-optimizer/pob2opt/catalog/scope.py:86`, `resolve_target_skills`.

The resolver accepts every ID found in exactly one of the gem/granted-skill tables. It never checks that the entity represents the registered objective's required skill. A request selecting an unrelated skill, or selecting both Flicker Strike and an unrelated skill, passes both `validate_record` and `resolve_objective_scope`. A future caller following the documented preparation path therefore receives a successful scope report for the wrong optimization problem. Hashing that selection makes it distinct but does not make it a Flicker Strike objective.

The independent probe supplies a synthetic catalog containing a Flicker Strike entity and an explicitly unrelated entity. All three selections return `scope_ok: true` on both interpreters. This is a contract counterexample, not evidence about actual game mechanics.

Required repair: resolve the objective's expected skill identities against the accepted catalog and check that all supplied IDs are valid representations of that skill. Check the gem/granted-skill relationship when both are supplied. Missing or ambiguous evidence must return an actionable scope issue; do not silently replace an incorrect selection. The expected mapping must come from the accepted catalog/scope, not from treating any exact ID or display-name match as approval.

Acceptance cases: the approved Flicker identity succeeds; a different active skill, a support gem, and a mixed or mismatched gem/granted-skill pair fail. Preserve the existing unknown-ID, ambiguous-name and class-parent checks. No prepare service or damage evaluator is needed to enforce this resolver contract.

## R2 P2 Enforce aggregate binding at persistence and corpus validation

Location: `pob2-optimizer/pob2opt/domain/validation.py:886`, `aggregate_binding_errors`; integration points are `storage/repositories.py:247` and `:705`.

The new binding helper correctly detects a wrong objective/hash but has no production caller. `RunStore.put_normalized` and `validate_stored` only use record validation and identifier resolution. Consequently, a schema-valid aggregate can cite an existing v2 manifest while carrying a different objective or objective hash, be accepted with reference checking enabled, and subsequently pass stored-corpus validation.

The independent probe seeds a closed fixture corpus, persists a v2 manifest through the normal reference-checked API, and inserts three conflicting aggregates. Wrong hash, wrong objective, and a legacy aggregate assigned to the v2 run all persist and revalidate successfully. Calling the helper separately reports `objective_hash_mismatch`, `objective_mismatch`, and `unbound_objective`, respectively. No staging escape hatch is used.

Required repair: resolve an aggregate's manifest from the store or pending import batch and run the binding check before accepting it. Include that check in stored-corpus validation so previously staged/imported conflicts remain visible. Preserve valid historical v1 aggregates in v1 runs. This concerns the existing persistence boundary; completing prepare or ranking is not required.

Acceptance cases: reject wrong objective ID/version/hash through single-record writes and batch imports, including a manifest in the same batch regardless of ordering. Reject v1 aggregates assigned to v2 runs. Accept a correctly bound v2 aggregate and the existing v1 corpus. Deliberately staged conflicts must make corpus/bundle validation fail rather than appear ready.
