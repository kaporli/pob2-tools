Reviewed 2026-10-17 against specification 1.1, delivery row P02-T01.1.
PR #13 head: `5981ee023ff5146c417de275d399a0991833ffe3`.
Verdict: **changes required before merge**. The investigation and explicit
limitations are useful, but the containment implementation has three gaps.
No reliability or four-hour-search gate is accepted by this review.

## R1 P1 Enforce the hard limit when a worker replies

Location: `pob2-optimizer/pob2opt/evaluation/adapter.py:230`–`233`, and
`WorkerHandle.request` at lines 204–208.

`_wait` returns immediately when the pipe is readable, before checking memory.
After a successful response, `request` samples memory but never compares that
measurement with the hard limit. A responsive worker can therefore exceed
the hard limit, return a successful evaluation and remain alive. The default
soft threshold can recycle it on a later operation, but that does not enforce
the hard-limit failure contract or stop it while the adapter is idle.

The independent probe uses the PR's real synthetic worker and real Windows
memory measurement: an 80 MiB hard limit, no soft recycle, and an 80 MiB
allocation during `primitives`. On Python 3.12 it returns a result while holding
109,559,808 bytes; on 3.10, 106,205,184 bytes. Both workers remain alive above
the 83,886,080-byte limit. A separate injected measurement of 500 MiB against
a 400 MiB limit reproduces the same path deterministically.

Required repair: enforce the hard limit at the reply/startup boundary and
before reusing a worker, as well as during waits. If a completed operation
reveals a breach, terminate the worker and report `EngineMemoryLimit` rather
than accepting its result. Retain the measurement and death reason.

Acceptance: fast replies above the limit fail, a startup ready frame cannot
bypass the bound, and a fresh worker can complete the next valid operation.
Keep the existing slow-runaway test. Document that periodic sampling allows
overshoot; it is not an OS-enforced allocation ceiling.

## R2 P2 Count fatal startup and reply failures toward replacement exhaustion

Location: `pob2-optimizer/pob2opt/evaluation/adapter.py:449`–`457` and
`_request` at lines 550–552.

The failure counter increments only for `EngineCrash` and `EngineTimeout`.
Worker initialization exceptions and unexpected handler exceptions arrive as
fatal `EngineInternalError` responses, which terminate the worker but do not
consume the replacement budget. With `max_consecutive_failures=2`, five
consecutive startup failures launch five workers and leave the counter at
zero. Five fatal handler replies do the same. The caller can keep requesting
work and spawning workers indefinitely despite the configured loss cap.

Startup losses also escape the history: `WorkerHandle` raises before the
adapter saves it. Even startup memory kills, which do increment the counter,
leave `worker_history` and `worker_pids` empty; exhaustion says `Last: none`.
This removes the evidence the task requires for failed workers.

Required repair: account for every unplanned worker death, including fatal
internal errors, and retain startup lifecycle/peak/reason information before
propagating its typed failure. Keep live nonfatal input refusals and planned
recycles distinct. Preserve the original error type and do not retry failed
requests automatically.

Acceptance: repeated startup exceptions, fatal handler replies, startup
timeouts and memory kills all stop at the configured budget. Every ended
worker has one history entry, including startup failures. A genuinely
successful complete operation resets the count; planned recycling does not
consume it.

## R3 P2 Refuse bounded execution when memory cannot be measured

Location: `pob2-optimizer/pob2opt/evaluation/adapter.py:215`–`218` and
`_wait` at lines 233–234; `evaluation/memory.py` returns `None` on probe failure.

The constructor checks that a probe implementation exists for the platform,
but a failed read from a live worker is silently ignored. `sample_memory`
keeps its previous value, and `_wait` skips enforcement for `None`. A bound
can thus become unenforceable without any error or warning. This applies at
startup as well as after previously successful samples.

The injected probe returns `None` while a real synthetic worker deliberately
takes 300 ms to answer. Both interpreters attempt several samples and then
return a successful result with the worker still alive. This is fault
injection of the documented read-failure return value, not an observed OS
failure on this machine.

Required repair: when a live worker cannot be measured under a requested
memory bound, use a bounded recovery policy or terminate/refuse with a typed
diagnostic. Distinguish process exit from inability to observe a live process.
Never reuse stale measurements as evidence of a current bound.

Acceptance: missing measurements during startup, a slow request and after a
previous good sample produce a visible bounded failure. Explicitly unbounded
mode must continue to work without a probe.
