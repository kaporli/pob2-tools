## Implemented behavior

Input: a P01 `BuildSpec`, the `ItemInstance` records for its equipped items and
socketed jewels, and a `CatalogNaming` table mapping catalog IDs to PoB names.
Output: a PoB document, a report of everything the document could not carry,
and a round-trip comparison against canonical identity.

Previously a BuildSpec could not be written out at all.
`pob2opt/evaluation/documents.py` said so and named P02-T05 as the owner, so
the only document an engine evaluation could use was the original blob the
build was parsed from. On the Lua side, `convert_trade_item` read seven
modifier arrays and emitted four, writing its defaults back into the caller's
item object while doing it (research F12).

Now:

* **`naming.py`** holds the catalog ID to PoB name tables. Nothing in the
  exporter invents a name: a lookup miss is an `UnresolvedName`, which becomes
  a reported unsupported field. A table that is not injective is refused
  outright, because a document written with it could not be read back. P02-T02
  produces the real table; the tests supply a synthetic one.
* **`support.py`** is the report. One `UnsupportedField` carries the field
  path, the reason, the value itself and whether the field is inside the
  canonical identity. An export losing anything inside the identity is
  `incomplete` and `recommended_deliverable` is false. A loss outside it (a
  record name, a listing ID, provenance) is still reported, with its value, so
  a caller can keep it out of band.
* **`itemtext.py`** writes an `ItemInstance` as PoB item text and reads one
  back. Every `ModifierCategory` except `unknown` round trips, using the same
  markers PoB's own `Item:BuildRaw` writes. Reading follows PoB's own line
  handling (`%s*([^\n]*%S)`): blank lines dropped, each line trimmed, the
  `Implicits: N` count deciding where the implicit block ends.
* **`builddoc.py`** writes a `BuildSpec` as a `PathOfBuilding2` document and
  reads one back: `Build`, one `SkillSet`, one `Spec`, one `ItemSet`, one
  `ConfigSet`. It writes `characterLevelAutoMode="false"` so PoB does not
  recompute the level from the tree (observation P00-OBS-02), and it unions
  weapon-set allocations into `Spec@nodes`, because PoB reads the allocation
  from there and only the set from `WeaponSetN`.
* **`roundtrip.py`** exports, reimports and compares `build_identity` and
  `item_identity` leaf by leaf. It hashes the canonical JSON of the whole
  input before and after and raises `SourceMutated` if either direction changed
  it.
* **`bootstrap.lua` `convert_trade_item`** emits all seven modifier arrays,
  reads each one with `or {}` at the point of use so the caller's item is not
  written to, and returns `emitted_mod_counts`, `unsupported` and `complete`
  alongside `item_string`. Unknown item fields, unknown property names,
  requirements other than level and socket detail are named with their values
  rather than dropped. Only that handler changed; `load_build_xml` and
  `buildSummary` are untouched.

### Loading the exported XML in the pinned PoB

`docs/evidence/P02/roundtrip-pob-export.xml` is our export of a build PoB
itself saved. Two ways to load it, both on the pinned checkout `ce566ea`:

1. **In the PoB application.** Copy the file into PoB's build folder, giving
   it a `.xml` extension, and open it from the build list. The checkout in use
   here is a headless one with no build folder of its own; on a normal install
   the folder is the one PoB's "Builds" list points at.
2. **Through the engine bridge**, which is what the recorded evidence used and
   needs no GUI:

```python
import os
from pob2mcp.engine import Pob2Engine

engine = Pob2Engine(os.environ["POB2_ROOT"])
xml = open("docs/evidence/P02/roundtrip-pob-export.xml", encoding="utf-8").read()
print(engine.call("load_build_xml", {"xml": xml}))
engine.close()
```

`load_build_xml` raises on a document PoB cannot read (observation P00-OBS-01),
so a clean return is the load. The summary it prints should read
`allocatedNodes: 36`, `equippedItems: 1`, `socketGroups: 1`, `class: Ranger`,
`level: 28`, which is what `docs/evidence/P02/roundtrips.json` records for the
build PoB saved before the export.

`docs/evidence/P02/roundtrip-synthetic.xml` is **not** for loading: its class,
skills and bases are invented, so PoB will read the file and find none of those
entities. It is there to be read as the shape the exporter produces.

Minimal end-to-end example, offline:

```python
from pob2opt.evaluation import CatalogNaming, round_trip

report = round_trip(build, items, naming)
report.status                    # "faithful", "incomplete" or "unfaithful"
report.recommended_deliverable   # False unless faithful
[u.field_path for u in report.export.identity_losses]
report.document                  # the PoB XML
```

## Adverse cases

Exercised:

* a skill that triggers another: reported, incomplete, nested skill IDs
  preserved;
* quest flags, reward flags and point budgets: reported, incomplete, all four
  values preserved;
* a socket group granted by an item: reported, incomplete, because PoB
  regenerates item-granted groups and discards a group whose `source` string it
  does not recognise;
* a class, ascendancy and passive with no entry in the naming table: reported
  as `unresolved_name` with the ID preserved, never guessed;
* a naming table mapping two catalog IDs to one PoB name: refused before
  anything is written;
* an item hash with no `ItemInstance` supplied: reported, and the slot is not
  quietly written as empty;
* `ModifierCategory.unknown`: reported, and the line is not written, because
  writing it unmarked would turn it into an explicit;
* a modifier carrying `native_id`, `resolved_effect_ids`, a roll range and a
  non-resolved parse status: all four reported with their values;
* a flag recorded `false`: reported, because PoB writes only the positive line,
  so `false` and absent become the same document. This is the
  absent/null/zero/false distinction from `contracts.md` hitting a format that
  does not have it;
* modifier source positions PoB would renumber, and positions that interleave
  the implicit and explicit blocks;
* a requirement other than level;
* an item with every optional field omitted, item text with no `Rarity:` line,
  a modifier line containing a colon, and empty item text (refused, not
  invented);
* a weapon set that leaves no trace in a document, and equipment that implies a
  weapon set the build does not declare: both reported;
* a damaged export in the engine lane, so the equality assertions cannot pass
  on an empty document;
* an unknown trade item field and an unknown trade property name through
  `convert_trade_item`.

Not tested:

* a build with more than two weapon sets. The exporter reports it as
  unsupported from the naming table's set number, but no fixture exercises a
  catalog that declares three.
* real PoE 2 catalog IDs. Every naming table here is either synthetic or
  derived from a document PoB wrote by prefixing PoB's own names. The real
  table is P02-T02's deliverable, and the exporter's behaviour against it is
  unverified.
* unique items with alternate variants (`variantAlt` and its four siblings),
  mastery effects, per-node notes, custom modifier blocks and PoB's
  `Placeholder` config inputs. The exporter does not write them and the
  importer does not read them; an imported document carrying them loses them
  silently, which is a gap, not a reported loss. See the deviations below.
* an item with linked sockets. PoE 2 sockets are not linked, so the exporter
  writes one group per socket and reports anything else; no fixture carries a
  linked group.
* more than one skill set, item set or config set. PoB supports several; this
  writes one and reads the first.

## Deviations and unresolved questions

1. **`CatalogNaming` is a new caller-supplied input, not a schema change.** No
   record changed, `python scripts/generate_schemas.py --check` still reports
   20 matching files, and nothing was added to `pob2opt/domain/records.py`. The
   table is the catalog translation P02-T02 owns; until it exists, an exporter
   either takes the table from its caller or invents PoB names, and inventing
   them is the failure this task is meant to prevent. Flag it if the reviewer
   reads a new boundary type as a contract change.
2. **`SocketedEntity.entity_id` is read as the socketed item's `item_hash`.**
   `contracts.md` does not say what an entity ID is. The exporter needs a
   reference it can resolve to an `ItemInstance` to write the jewel out, and
   the item hash is the only identifier the build already carries for an item.
   This is an interpretation, and it is the kind of thing `review.md` says an
   engineer must not settle alone. A build whose `entity_id` is anything else
   is reported as unresolved rather than mis-written.
3. **A support gem has no level or quality in a BuildSpec.** `SkillEntry`
   carries `support_ids: list[str]` and nothing else, so the document omits
   `level` and `quality` on a support gem and PoB applies its own default. The
   export reports this as `partial` and marks it as not affecting identity,
   because the record has nothing to lose, but it does mean an exported
   document is not a faithful PoB build when supports matter. The record is the
   gap, not the exporter. Owner: whoever revises `SkillEntry`, probably P04-T01.
4. **Ordinary and ascendancy allocations are split by a declared node set.**
   PoB keeps both in one `nodes` list. Without
   `CatalogNaming.ascendancy_node_ids` the split cannot be read back, so the
   export reports it. The real set comes from the tree data, which is P02-T02.
5. **Supports are recognised by a declared ID set, not by their position.** A
   PoB socket group is a flat gem list. The importer attaches a gem to the
   preceding active when its catalog ID is in
   `CatalogNaming.support_skill_ids`. A support that is not declared reads back
   as another active skill, and the export says so.
6. **The importer reads only the first skill set, item set and config set.**
   PoB supports several of each. A document with more loses the rest, and the
   importer does not report it, because the report belongs to the export side.
   This is a gap in coverage, not a silent loss on the path this task owns, but
   it will matter to P04 when real community builds arrive.
7. **PoB document features the exporter does not write.** Alternate unique
   variants, mastery effects, per-node notes, custom modifier blocks,
   `Placeholder` config inputs, `ModRange` elements and `Spectre`/`BeastCompanion`
   entries. None has a BuildSpec field, so nothing is lost on export; a
   document carrying them loses them on import, unreported. Recorded as a gap.
8. **`convert_trade_item` now returns more keys.** `item_string` is unchanged
   in meaning and both existing callers (`pob2mcp/server.py`,
   `pob2opt/harvest.py`) read only that key, so the change is additive. The
   repair also changes what that string contains for any item carrying a
   fractured, desecrated or crafted modifier: those items now produce different
   stats, which invalidates any stored evaluation of a converted trade item.
   `review.md` calls this out under "Parser/item-conversion change"; no such
   evaluation is stored in this repository today.
9. **Blocked: nothing.** The submodule is still absent and was deliberately not
   restored; `POB2_ROOT` covers the engine lane, as P00 recorded.

## Request for review

Requested verdict: **accepted for P02-T05**, by a reviewer who did not write
this code. I wrote the implementation and its tests, and the place a
self-review is weakest is the honesty of the support report: a loss that is
reported but not real, or real but not reported, both pass a test suite written
by the same person. Two invariants are asserted for that reason
(`test_a_complete_export_never_differs_on_reimport` and
`test_every_reported_identity_loss_names_a_field_that_actually_differs`), and
they are the right place for an independent adversarial case, ideally a real
community build rather than a fixture.

No gate is requested. The two open interpretations for the reviewer are
deviation 2 (`entity_id`) and deviation 3 (support gem level), and the
regression rule in `review.md` for an item-conversion change applies to the F12
repair.
