## Reproduction

Working directory: the repository root. Prerequisites: the dev install from
`tests/MANIFEST.md`. No PoB, no credentials, no network.

```
python scripts/p09_t01_suite.py
python -m pytest tests/unit/test_p09_t01_scenarios.py tests/unit/test_p09_t01_protocol.py -q
python -m pytest tests/unit -q
python scripts/generate_schemas.py --check
```

The generator prints the suite id, the fixture path and SHA-256, the three
artefact paths, the record counts and the `baseline_suite_hash`. It is
deterministic: rerunning it on an unchanged tree rewrites identical bytes, and
`tests/unit/test_fixture_manifest.py` fails if they differ from the recorded
hash.

Minimal end-to-end example, for whoever builds P07:

```python
import json
from pob2opt.domain.codec import from_jsonable
from pob2opt.domain.records import ScenarioSpec, RotationPolicy

bundle = json.load(open("tests/fixtures/combat/p09_synthetic_suite.v1.json", encoding="utf-8"))
scenarios = [from_jsonable(ScenarioSpec, s) for s in bundle["records"]["scenario_spec"]]
rotations = [from_jsonable(RotationPolicy, r) for r in bundle["records"]["rotation_policy"]]
oracle = bundle["oracle"]
```

Evaluate, then check the result against `oracle`: total target health, route
time, targetable time and untargetable time. Nothing in that check is a claim
about the game, and any `EvaluationResult` produced this way carries
`validation: synthetic_only`.

## Adverse cases

Exercised:

- A field marked `unresolved_input` with no gap, and a field marked `sourced`
  with a gap: both fail `test_every_row_is_sourced_or_unresolved_and_never_both`.
  This is the guard against a number arriving without a named owner.
- A gap id named in the field table that does not exist in the bundle: fails
  `test_every_named_gap_exists_in_the_bundle`.
- A `ScenarioSpec` field added to the dataclass and not to the field table:
  fails `test_the_field_table_covers_every_scenario_spec_field`.
- A row claiming `measured` as its basis: fails
  `test_no_field_claims_a_direct_measurement`.
- A family identifier appearing anywhere in the bundle: fails
  `test_no_build_family_is_named_anywhere_in_the_suite`.
- A reference slot quietly filled: fails
  `test_no_scenario_has_been_given_a_reference`.
- An edited fixture: fails both `test_the_committed_bundle_is_what_the_generator_produces`
  and the recorded SHA-256 in `tests/fixtures/manifest.json`.
- A `DataGap` whose `needed_evidence` is vacuous: rejected by the P01 validator
  inside the generator before anything is written.
- A boss rotation with no rule for an untargetable target: fails
  `test_the_boss_rotation_can_stop_attacking`.

Untested, and important:

- Nothing has run these scenarios through an encounter evaluator, because no
  evaluator exists. `validation_status` is `untested` for that reason, and the
  oracle is an expectation, not a verified result.
- The oracle checks arithmetic over the declared constants. It cannot catch a
  modelling error in a future evaluator that happens to reproduce those totals
  for the wrong reason.
- No representative scenario was written, so the claim that a representative
  `ScenarioSpec` cannot be stored half-filled with nulls is an argument from the
  contract's nullability rules, not a failed attempt recorded in a test.
- The two clear shapes are distinguished only by cluster size and declared route
  legs. Whether that is enough to separate clearing builds in practice is
  unknown and will stay unknown until encounters are measured.

## Deviations and unresolved questions

**The corpus-dependent half of this task is blocked, and the deliverable is
short by design.** P09-T01 asks for three Huntress build families selected from
the source corpus, with their exact required mechanics, and for reference builds
per scenario. There is no source corpus. P03-T01 recorded on 2026-10-10 that
Mobalytics returns HTTP 403 to this client on every build path including its own
terms page, that Maxroll's `robots.txt` prohibits automated retrieval outright
and names this client's agent family in a disallow-all group, and that poe.ninja
documents its builds and profiles API as internal and not available for
third-party use. Naming three families now would mean inventing them, which is
the one thing this task exists to prevent. The selection is left open and
recorded as `gap-p09-t01-build-families`.

Consequences, stated plainly:

- Every `reference_build_id` and `reference_result_id` is null, so every ratio
  `r_i` in the ranking formula is unresolved and every aggregate score on this
  suite is null. The suite exercises an evaluator; it cannot rank anything.
- No constant was fitted and none is proposed. The floors of `scenarios.md`
  (0.50 per scenario, 0.80 per category) and the thresholds of P09-T03 stand
  unchanged. Reviewer acceptance of the protocol and the domain interpretation
  was the gate before fitting, and that gate was never reached because there was
  nothing to fit.
- The suite is `kind: synthetic` and `validation_status: untested` throughout.
  No result on it may be reported as map clear speed or boss kill time.

**Which `scenarios.md` shape each workload uses:** `p09-syn-clear-dense` is
`clear_dense`, `p09-syn-clear-spread` is `clear_spread`, `p09-syn-boss-short` is
`boss_short`, `p09-syn-boss-sustained` is `boss_sustained`. The shape is stored
inside each record at `initial_state.shape`, so it survives extraction.

**Contract and default changes proposed: none.** No schema change was required
and `python scripts/generate_schemas.py --check` passes unchanged.

**One observation for the reviewer, not a change request.** A representative
`ScenarioSpec` cannot be stored today even as a skeleton, because
`duration_limit_s`, `capability_floor_ratio` and the entity health fields are
required and non-nullable, so an unresolved value cannot be written as null in a
scenario record. The unresolved inputs therefore live in the `DataGap` records
and in `docs/evidence/P09/protocol-fields.json`. If the reviewer would rather
see a nullable representative skeleton, that is a `ScenarioSpec` change and a
migration test, and P09-T01 does not propose it.

**Decision record:** `docs/decisions/D04-encounter-suite.md`, proposing D04
blocked for practical claims. It names the two inputs that would unblock it: one
complete Huntress build the owner exports by hand, and recorded gameplay for one
named boss and one named map layout. Only the owner, or an operator the owner
names, can supply either.

**Blocked by this, and what can continue.** P09-T02 (observation collection),
P09-T03 (calibration) and P09-T04 (search comparisons) stay blocked on the same
two inputs. P07 is not blocked: it can be built and tested against
`p09-synthetic-v1` now, which is why the suite exists. P03-T02 local acquisition
is the cheapest next step, because it is the route a hand-exported build file
