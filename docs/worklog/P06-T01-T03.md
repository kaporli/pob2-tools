## Implemented behavior

New package `pob2opt/coverage/`:

| Module | Behavior |
|---|---|
| `registry.py` | `RuleEntry` wraps one contracts.md `MechanicRule` with the subjects that pull it in (`skill:`, `support:`, `passive:`, `config:`, `scenario:`, `always`), produced state paths, critical kind (`activation`, `attribution`), P09 gap ids, tests, damage-source flag, activation `satisfied_by`, attribution `assignments`, reviewer and required events. `MechanicsRegistry` refuses duplicate ids, unregistered dependencies, ambiguous owners and static cycles; `registry_hash` covers every calculation field, `closure_hash` identifies the rules one evaluation used; titles are excluded. |
| `flicker_v1.py` | Registry `p06-flicker-v1`, 63 rules at `3cc334d` (64 after the repair below): every skill and support in the seed, the Martial Artist Combo nodes, charges, Combo, Rage, mana cost/regeneration/flask/sustain, Flicker timing, Hit and Run activation and speed, Charged Staff consumption, attribution, initial state, the Pinnacle target, the engine pin, the patch profile and two PoB config defaults. `POB_CYCLE_INPUT_RULES` maps each `pob-cycle-v1` input to its rule. |
| `inputs.py` | Offline readers: PoB XML to `BuildFacts` (groups with weapon-set bindings, nodes, items, explicit config); the engine probe's per-line parse verdicts and applied config; option headers from `ConfigOptions.lua`; scenarios and P09 gaps from `scenarios.json`. |
| `analysis.py` | `analyse(build, scenario, registry, rotation=, mod_support=, ...)` walks active groups, supports, nodes, item lines, applied config, rotation actions and predicates, scenario fields and required rule inputs; returns per-domain coverage/validation states and findings rendered as validated `DataGap`s. `decide(report, registry)` refuses on any blocking finding or open blocking P09 gap, on any unsettled activation/attribution rule regardless of severity, and on a report made under another registry hash. |
| `resolution.py` | `CoverageLedger.resolve` accepts a `Resolution` only with evidence, a known gap and a corrected rule or input; bumps the rule version, records author/reviewer, resolves the gap, supersedes tracked evaluations whose rules (or dependents) or inputs changed. A differing outcome for an already resolved rule marks it `contradicted` and reopens the gap as `conflicting_evidence`. `invalidate_for_patch` marks rules touching changed entities, unknown-impact families or (no diff) everything stale with their dependents; others carry forward; display-only changes do nothing. |

Scripts: `scripts/p06_seed_engine_mod_support.py` (engine, refuses an unpinned
or dirty checkout) and `scripts/p06_seed_coverage.py` (offline, `--check`).

Finding classes and the request each produces: `missing_data`,
`missing_implementation`, `unknown_rule`, `unvalidated`, `stale_patch`,
`unknown_entity`, `hidden_assumption`, `activation_unmet`,
`unassigned_damage`, `conflicting_evidence`, `not_applicable`. They map onto
the contracts.md gap kinds; the collection method differs per class.

## Deviations and unresolved questions

- `RuleEntry` carries P06 fields outside the persisted `MechanicRule`
  record; no schema changed. Persisting registries is not implemented.
- Severity policy: any unsupported or unknown rule pulled in by an enabled
  group on the active weapon set blocks, unless the scenario lacks the events
  it needs. This is conservative; a reviewer may narrow it.
- The PoB charge table notes a "consumed a Power Charge Recently" condition in
  the 0-charge row; no registry rule names it yet.
