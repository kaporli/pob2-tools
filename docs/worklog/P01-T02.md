## Implemented behavior

Input: validated records from P01-T01. Previously nothing had a content identity, and the legacy pipeline keyed its cache by bare filename (P00 finding F05).

Resulting behavior: `pob2opt/domain/identity.py` defines one *identity projection* per thing that can be identified, and hashes its canonical JSON. A projection is a plain dict holding only the fields that define that thing, so the included and excluded sets are literally the code, not a comment that can drift from it.

Canonical form: UTF-8 JSON, keys sorted, compact separators, `allow_nan=False`, `ensure_ascii=False`.

| Function | Identifies |
|---|---|
| `document_hash(bytes)` | Raw source bytes. Not canonical JSON: a line-ending difference in a source is a different document. |
| `item_hash` | An item's resolved content. |
| `listing_snapshot_hash` | The acquisition side: price, currency, availability, timestamps, quantity. |
| `build_hash` | Every gameplay choice. |
| `rotation_hash` | Category and ordered rules. |
| `scenario_hash` | Everything that changes what is simulated. |
| `baseline_suite_hash` | The references a campaign is scored against. |
| `manifest_hash` | A whole run manifest, metadata included. |

### Included and excluded

The full list is in the `identity.py` module docstring, as the task requires. The decisions a reviewer is most likely to challenge:

- **`listing_id` is excluded from `build_hash`.** Equipment hashes the item, not how it was bought, so an equal-stat item at a different price is the same build (acceptance example 8).
- **`catalog_hash` is excluded from `item_hash` and `build_hash`.** The item is identified by its resolved content, and `resolved_effect_ids` already carries whatever the catalog resolved. Catalog identity enters an evaluation through the cache key, where a catalog change must invalidate results, rather than through the item hash, where it would fork every item on every patch bump.
- **`skill_group_id` is excluded.** It is a structural label from the source file; two gameplay-identical builds that numbered their groups differently are the same build.
- **A config value's `origin` and `verified` flag are excluded, its value is not.** Where a setting came from is provenance; what it is set to is gameplay.
- **`reference_build_id` and `reference_result_id` are excluded from `scenario_hash`** and included in `baseline_suite_hash`. Freezing a new reference must start a new leaderboard without invalidating candidate evaluations.
- **`rotation_ids` are excluded from `build_hash`.** contracts.md: rotation identity is separate and enters evaluation identity there.

### Ordering

Passive allocations, ascendancy allocations and per-set allocations are sorted, after P01-T01 has rejected duplicates, so import order cannot fork identity. Skill groups, the skills inside them, their support lists and rotation rules keep their order, because order is semantic there.

## Adverse cases

Exercised: NaN, Infinity and negative infinity refused by `canonical_json`; `document_hash` refused a `str` rather than silently encoding it; CRLF inside a gameplay string (modifier text) *does* change item identity while CRLF in metadata does not; an unknown price and a zero price produce different listing snapshots; an absent predicate member never reaches a hash.

Not tested: identity stability across machines and Python builds. The hashes are SHA-256 over sorted-key UTF-8 JSON, which has no documented platform dependence, but only this machine was used. A second machine should be checked before any cross-machine cache or shared corpus is relied on.

Also not tested: whether the excluded sets are the *right* ones for real PoE 2 content. They follow contracts.md and are exercised against synthetic records only. A real parser (P04) or catalog (P02-T02) may show that a field currently treated as metadata is gameplay-relevant; that is a projection change and invalidates affected hashes, which the review procedure already covers under parser and catalog regression rules.

## Artifacts and provenance

Synthetic only, the same fixture records as P01-T01. Content hashes recorded inside those fixtures are re-derived by `::test_hashes_are_stable_across_calls_and_processes`, which fails loudly if a projection changes, rather than letting the fixture drift.

No PoB-derived and no independently measured evidence is involved.

## Deviations and unresolved questions

1. `catalog_hash`, `skill_group_id` and the config `origin`/`verified` flags are excluded, as argued above. These are judgement calls inside the contract rather than contract changes, but they are the ones most worth a reviewer's disagreement.
2. `rotation_hash` excludes `version`. A version bump with identical rules is the same policy; a rule change changes the hash by itself.
3. `scenario_hash` includes `scenario_id` and `version` but excludes `evidence_ids` and `validation_status`. Promoting a scenario from `fixture_checked` to `gameplay_checked` must not invalidate the evaluations run under it.
