## Implemented behavior

Input: a catalog profile request file naming the game, realm, league and a
directory of official release captures, plus either a PoB checkout or a saved
row capture.

Previously there was no catalog at all. `pob2opt.catalog` did not exist, no
record described the pinned engine's entities, nothing resolved a game patch,
and the only character rule anywhere was `(args.level - 1) + 8` in
`cli.py:374`, a comment-sourced guess at the passive point budget. `doctor`
asserted `patch_profile_owner == "P02-T02"` as a forward reference to work
that had not been done.

Now `pob2opt catalog export --profile FILE --out DIR` writes a self-contained
bundle: a `GameCatalog` of 24 355 entities across the ten tables
`records.CATALOG_TABLES` declares, the `PatchProfile` that pins it, every
`DataGap` the rules could not close, and a `SourceDocument` plus its bytes for
each piece of evidence any of them cites. Every reference inside the bundle
resolves inside the bundle, and the export validates its own output before it
returns; a bundle that does not validate is exit 4.

### Typed Lua bridge operations

Nine handlers appended to `pob2-mcp/pob2mcp/bootstrap.lua`, immediately before
the dispatch section, after the existing `misc` section. `convert_trade_item`
and `load_build_xml` are untouched. Eight return the same paged envelope
(`table`, `total`, `offset`, `next_offset`, `rows`) over a sorted native key,
so paging is stable and two runs over one checkout produce the same bytes;
`catalog_rule_sources` returns one structured read of the upstream facts the
rules are derived from. All nine are read-only: an engine test asserts that a
catalog read between two evaluations does not reload the build or change a
single primitive value.

`EngineAdapter.catalog_page` and `catalog_rows` are the coordinator side, so
catalog reads inherit P02-T01's bounds, worker replacement and typed failures.
An unknown table is refused in the worker as `unsupported` and the worker
survives it.

### Entity identity

Every entity is keyed on the native upstream key, namespaced
`poe2/<table>/<native key>`; the patch and catalog scope come from the
`GameCatalog` the entity lives in, which carries both `catalog_hash` and
`patch_profile_id`. On this checkout that keeps 4 distinct gems named
`Mace Strike`/`Lightning Bolt`/`Spear Stab`, 577 distinct passive nodes that
share a name with another node, and 108 distinct granted skills that do, all
separate. Modifier ids repeat across upstream mod groups, so a modifier's id
is the pair. `passive_edges` and `ascendancies` are derived from the node and
class rows rather than read twice; an edge reported from both ends is stored
once, and a link to a node outside the export is not an edge.

`raw_reference` keeps the row as the engine reported it. Nothing is flattened
and no modifier is summed.

### Patch resolution and evidence

The live patch comes from `docs/evidence/P02/release/*.json`, captures of
official pages made out of band, and from nothing else. The export never
reaches the network: an export that could fetch a patch id could also fetch it
wrong, and `tests/unit` runs with sockets blocked. With no capture the profile
records `patch_id: "unknown"`, compatibility `unknown`, and a blocking gap
naming the page that has to be captured.

The one capture committed here is for patch `0.5.5e`, from the official Early
Access Patch Notes thread, read on 2026-10-06. **It is labelled
`fidelity: "summary"`**: the page was fetched and reduced by a language model,
so the stored excerpt is a reported reading of three bullet lines, not stored
source bytes. A summary capture can name the patch and can never support
`verified` compatibility; the export records that as a gap every time.

### Compatibility, decided by fixtures

`pob2opt/catalog/fixtures/compatibility.json` is a fixed set of 18 fixtures of
four kinds: availability (an entity is present under its id and name), field
(a named upstream value is unchanged), count (a floor per table) and behaviour
(the engine's own answers for one pinned document, inside a relative
tolerance). Behaviour fixtures exist because availability cannot tell a
renamed field from a changed formula.

The verdict, worst condition first: no patch evidence, or a fixture that could
not run, is `unknown`; a profile pinned to a patch that is no longer live is
`stale`; a failed fixture, an engine release older than the live patch, a
summary capture, a dirty checkout or an open blocking gap is `partial`;
`verified` needs all of those clear. On this checkout the answer is
**`partial`** for four stated reasons, and the offline lane's answer is
`unknown` because it has no engine to run the behaviour half. An unchecked
fixture is not a pass.

A fixture caught a mistake of mine while I was writing it: I recorded
`Long Quarterstaff` as type `Quarterstaff` from memory, and the set rejected
it. Upstream files it as type `Staff`, subType `Warstaff`. The fixture file
says so.

### Evaluation context identity

`catalog.context_identity` projects the profile to what changes an answer:
game, realm, league, patch id, catalog hash, PoB commit, dirty hash, adapter
version and the compatibility verdict. Changing the upstream commit changes
the hash; so does a changed dirty hash, a changed catalog, or the same catalog
accepted at a different verdict. `resolved_at`, `record_id` and the evidence
lists do not.

## Adverse cases

Exercised:

* no release evidence at all: `patch_id: "unknown"`, compatibility `unknown`,
  a blocking gap naming the page to capture;
* an empty release directory, a capture with an unknown `fidelity`, one
  missing its `patch_id`, and one from a future capture format: each refused
  with the field named;
* a summary capture: the patch resolves, compatibility cannot reach verified,
  and a gap says why;
* an engine release older than the live patch: `partial`, with the two dates
  in the reason;
* a pinned source pattern that no longer matches: the rule becomes a gap, or,
  for the level cap and the point maximums, the export refuses with exit 3 and
  names the pattern;
* an entity removed from a table, and an entity renamed: `absent` and
  `mismatch` respectively, from the real shipped fixture set;
* a behaviour fixture whose engine raises: `mismatch`, never a pass;
* an unknown catalog table: typed `unsupported` in the worker, which survives;
* a build naming a class the catalog does not have, and a build document that
  is not XML: both reported as unresolved rather than invented;
* an unreadable request file, an unknown request key, a future request schema,
  and no engine at all: exit 2, 2, 2 and 3;
* a profile pinned to an earlier patch, with and without a capture for it;
* a catalog read in the middle of an evaluation: no reload, identical values.

Not tested:

* a real patch transition. Everything about `stale` and about an engine
  predating a patch is exercised against one captured patch and one engine
  release. A second capture, taken after the next release, is the only thing
  that tests the transition for real.
* a `verified` verdict end to end. The unit test reaches it through
  `decide_compatibility` with all conditions met; no export on this machine
  can, because the checkout is dirty, the capture is a summary and a blocking
  gap is open. That is three independent reasons, each of them true.
* the behaviour fixture set is one document and eight values. It would catch a
  changed life-per-level or class base attribute; it would not catch a changed
  damage formula.
* `item_modifiers` weights and trade hashes are exported but nothing reads
  them yet, so their shape is unvalidated by any consumer.
* no gameplay evidence exists for anything here, and none is claimed.

## Deviations and unresolved questions

1. **`ADAPTER_VERSION` moved from `p02-t01.2` to `p02-t02.0`.** Its docstring
   says to bump it whenever the adapter changes what it asks the engine for.
   It can now ask for a catalog page, so it did. The primitive path is
   unchanged and no stored evaluation exists to invalidate.
2. **A profile pinned to a different adapter is now refused.** The P02-T01
   review listed this under "concerns, not defects" and said P02-T02 owns the
   profile. `_check_profile` now compares `adapter_version`. Four P02-T01
   call sites repin the shared fixture, exactly as they already repinned
   `pob_commit`. If the reviewer reads this as out of scope, it is one `if`
   and four one-line fixture changes to revert.
3. **`quiet` now redirects file descriptor 1.** Rebinding `sys.stdout` did
   not stop PoB's Lua writing its startup text to the inherited handle, which
   corrupted the JSON this command writes to its own stdout. The worker never
   answers on stdout, so nothing is lost, and a failure to redirect is
   reported on stderr rather than being fatal.
4. **`EngineAdapter.probe` is new.** The behaviour fixtures run while the
   profile is being produced, so there is no `PatchProfile` to check them
   against and no `BuildSpec` behind them. `probe` returns a plain mapping
   rather than a `PrimitiveSnapshot`, so nothing can mistake its numbers for
   an evaluation. It is a narrow addition and it is a possible back door
   around `_check_profile`; the docstring says what it is for.
5. **The evaluation context hash lives in `pob2opt/catalog/context.py`, not
   in `domain/identity.py`.** `identity.py` is the canonical home for
   identity projections and this arguably belongs there. It is here to keep
   this change out of a P01 file other work is editing. Moving it is a
   rename; P08, which consumes `cache.py`, is the natural time.
6. **`compatibility` is part of the context identity.** A catalog accepted as
   partial and the same catalog accepted as verified are different claims, so
   a result cached under one is not served for the other. This is a judgement
   about cache identity that `architecture.md` does not spell out; it is
   conservative in the safe direction and an engine test shows its effect.
7. **The release capture is a summary, not a verbatim capture.** The task
   said to record `unknown`/`partial` if release evidence could not be
   obtained offline. Network access turned out to be available, so the patch
   is named from the official page, but what was stored is a model's reading
   of it. That is better than `unknown` and worse than evidence, and the
   format, the verdict and a gap all say so. Replacing it with a byte capture
   is a collection task, not an edit.
8. **No schema change.** `scripts/generate_schemas.py --check` passes
   unchanged; no record was added, removed or altered.
9. **`cli.py:374`'s `(level - 1) + 8` is still there.** It is the legacy
   phase pipeline, which `architecture.md` keeps as a comparison path. It is
   not read by anything in this change and the gap record names it so the
   next person does not mistake it for a validated rule.
10. **Blocked: nothing.** The submodule is still absent and was deliberately
    not restored.
