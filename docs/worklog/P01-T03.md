## Implemented behavior

Input: validated records with content identities. Previously the only persistence was `cli.save_phase`, which wrote `<out>/<phase>.json` with no manifest and served a cached result to any request (P00 finding F05).

Resulting behavior: `pob2opt/storage/` stores original bytes once, content-addressed and verified on read, and records as canonical JSON in SQLite with identifiers indexed beside them.

### One writer, one schema

`RunStore` owns every write, because architecture.md gives the coordinator the single writer. `transaction()` opens `BEGIN IMMEDIATE`, so a second writer fails fast rather than interleaving. Foreign keys are on; SQLite ignores them by default, and a task row pointing at an evaluation that was never written is exactly the inconsistency P01-T05 is about.

The same schema backs a corpus (`corpus.sqlite`) and a run bundle (`run.sqlite`). A run is a store that additionally has a manifest, tasks and copied references.

Tables: `blob`, `source_record`, `normalized_record`, `run`, `run_reference`, `evaluation`, `cache_decision`, `data_gap`, `observation`, `task`, `task_event`, `legacy_import`, plus `schema_migration`. Every payload table is `(identifiers..., status, created_at, json)`. There is no column per game stat, so a new modifier never needs a migration; `test_the_schema_has_no_column_per_game_stat` asserts the exact column set of `normalized_record`.

### Immutability

A record is inserted once under its `record_id` and never updated. Re-ingesting the identical record is a no-op; re-ingesting the same `record_id` with different content raises `DuplicateRecord`. The same external source acquired later is a *new* record with its own `record_id` and blob, so `source_history(provider, external_id)` returns what the source said and when.

### Blobs

`BlobStore` names a file by its SHA-256, sharded two characters deep. `put` returns `reused=True` and does not touch the file when the bytes are already stored; the test asserts the mtime is unchanged, not just that the hash matches. `get` re-hashes and raises `BlobCorrupt(expected, actual, path)` rather than returning wrong bytes. Writes go to a `.partial` sibling, are flushed and fsynced, and are then `os.replace`d, so an interrupted write leaves a partial file that `iter_incomplete()` lists and `iter_hashes()` ignores.

### Migrations

`MIGRATIONS` is a numbered tuple; each applies in its own transaction and records a checksum of its statements. Editing an applied migration raises `MigrationHistoryChanged`. A database written by a newer build raises `SchemaTooNew` instead of being downgraded.

### Ordering of the two writes

`ingest_source` writes the blob first and the row second. A crash between them leaves bytes nobody claims, which `orphan_blobs()` lists and the next ingestion of the same bytes reuses. The reverse order would leave a record pointing at bytes that were never stored, which is unrecoverable.

## Adverse cases

Exercised: a document whose declared `blob_hash` does not match the payload; a `record_id` reused for different content; a blob file tampered with after writing; blob names that are not SHA-256 hex; a foreign key violation; an edited migration; a database claiming migration 99; a failed acquisition that must be kept and must store no document; an invalid record offered to `put_normalized`; an `EvaluationResult` offered to `put_normalized`; a fault injected between the blob write and the transaction; a fault injected *inside* the transaction, via a SQL trigger, confirming the blob row and the record row commit together or not at all.

Not tested: concurrent writers. `BEGIN IMMEDIATE` and the single-writer rule are asserted by code and documentation, not by a test that runs two processes. That belongs with P08's real worker pool, and it is a real gap in this submission.

Not tested: a database large enough to exercise index choice, and recovery from a torn SQLite page. `PRAGMA synchronous = FULL` and WAL are set; neither was fault-injected at the filesystem level.

## Deviations and unresolved questions

1. **One schema for corpus and run.** architecture.md describes `corpus.sqlite` and `run.sqlite` as separate stores but does not say their schemas differ. They share one, which is why a run bundle can hold copied corpus records without a second table set.
2. **`RunStore` hosts `commit_evaluation`**, as interfaces.md names it, and also the source, normalized, gap, observation and run repositories. Splitting them into separate classes was not done because they share one connection and one transaction boundary; `commit_evaluation` writes the evaluation and closes the task in a single transaction, which a split would have to re-join.
3. **`_NORMALIZED_HASHES` lists which kinds the normalized table accepts.** An `EvaluationResult` is refused there because it has its own table. If P04 or P07 needs another kind normalized, that list is the one edit.
