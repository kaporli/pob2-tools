## Implemented behavior

Input: a run bundle with a database. Previously there was no task state at all; the legacy pipeline ran phases to completion in one process and had nothing to resume.

Resulting behavior: `pob2opt/storage/tasks.py` holds task state, recovery and checkpoints.

### States and transitions

`queued`, `running`, `completed`, `failed`, `cancelled`. `TASK_TRANSITIONS` in `pob2opt/domain/enums.py` is the whole legal set; anything else raises `TaskStateError`. `completed` and `cancelled` are terminal. `running -> queued` exists only for restart recovery.

Identity is `task_id` plus a `UNIQUE (run_id, generation_id, candidate_id)` index, so one candidate in one generation cannot be queued twice under two task IDs.

Every transition is one transaction that updates `task` and appends to `task_event`, so the state and its audit trail cannot disagree after a crash.

### Dispatch and completion are transactional

`dispatch` moves queued to running, increments `attempt` and records the worker, in one transaction. `RunStore.commit_evaluation(task_id, result)` writes the evaluation row and closes the task in one transaction, and is idempotent: a repeated completion message for the same task and the same evaluation is a no-op. A repeated message naming a *different* evaluation raises, because that is a bug, not a duplicate.

### Restart

`recover(run_id)` returns running tasks to queued. The attempt counter is not reset, and the interruption is written to `task_event`, so a repeatedly crashing candidate stays visible rather than looking fresh on every restart. Completed, failed and cancelled tasks are untouched.

`resume_plan` derives the plan from task rows, not from the checkpoint: after a crash the database is authoritative, and a checkpoint that disagrees is stale rather than a second opinion.

### Checkpoints

`write_checkpoint` writes a `.writing` sibling, flushes, fsyncs and `os.replace`s, so a reader never sees a half-written checkpoint. `validate_checkpoint` rejects a checkpoint whose `manifest_hash` or `run_id` does not match the run, because resuming would mix two runs.

### Reviewer inspection

`pob2opt/storage/queries.py` holds 15 named read-only queries, runnable by hand in `sqlite3` or all at once with `python -m pob2opt.storage.queries <db>`. They are documented, with output from the end-to-end example, in [docs/evidence/P01/inspection-queries.md](../evidence/P01/inspection-queries.md). `test_every_documented_query_runs_against_a_real_run` executes all of them against a populated database, so the queries a reviewer is told to use are known to work.

## Adverse cases

Exercised: dispatching an already-running task; moving a completed task; two task IDs claiming one candidate in one generation; a task claiming two different results; an engine timeout, which is recorded as a failed attempt with no evaluation row rather than a completed zero-score evaluation; a checkpoint from another manifest; a checkpoint from another run; an edited `manifest.json` on reopen; a missing checkpoint; a second evaluation row forced in under an existing cache key, refused by the `UNIQUE` index.

Not tested: real process crashes. Every interruption here is simulated by stopping the test at the point a crash would occur, which exercises the persisted state but not the operating system's behaviour on a hard kill, a power loss or a torn write. `synchronous = FULL`, WAL and the fsync-and-replace checkpoint write are the defences; none was verified against an actual power-loss or `TerminateProcess` event. P08-T04/T05 should do that with real workers and a four-hour soak.

Not tested: cancellation while a worker is mid-evaluation, and the interaction between a long engine timeout and coordinator cancellation that interfaces.md requires. There is no worker yet.

Not tested: more than one coordinator. The single-writer rule is enforced by `BEGIN IMMEDIATE` and by documentation, not by a test that runs two processes.

## Deviations and unresolved questions

1. **`resume_plan` recovers as a side effect.** Calling it returns running tasks to the queue and then reports the plan. That is convenient for a coordinator and surprising for a reader expecting a pure query; the docstring says so. If the reviewer prefers it split, `TaskStore.recover` and `TaskStore.by_state` already exist separately.
2. **Attempt counting.** `attempt` increments on dispatch, not on failure, so an interrupted attempt and a failed attempt both leave the counter at the number of times the task was handed to a worker. `task_event` distinguishes them. architecture.md allows "one fresh-worker attempt for an engine failure"; enforcing that limit is scheduling policy and belongs to P08, not to storage.
3. **`Checkpoint` is not a `RecordBase`.** It has `schema_version` and `created_at` but no `record_id` or `provenance_ids`, because contracts.md lists its fields without them and it is a file, not a corpus record. Same for `RunRequest`.
