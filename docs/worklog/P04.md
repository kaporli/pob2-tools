## Implemented behavior

### P02 follow-up: BuildSpec schema version 2

Before: a BuildSpec held only support IDs, so every export containing supports was incomplete and not recommendable (the PR #5 R2 guard). The importer also ignored `Build@mainSocketGroup`, and the exporter always wrote the first group with a main skill index, so a build whose main skill sat in group 2 changed its evaluated skill on a round trip; nothing reported it.

After: BuildSpec reads schema versions 1 and 2; every other record kind still reads 1. Version 2 adds `SkillEntry.supports` (one `SupportGem{support_id, gem_id, level, quality, enabled}` per `support_ids` entry, same order) and `BuildSpec.main_skill_group`. A null setting is unknown: the record cannot be `complete`, and the export omits the attribute, reports it and is not recommended. The PR #5 guard is kept for version 1 records and for unknown settings; it is relaxed only where the value is actually held.

The identity is versioned. A version 1 projection is byte-identical to before, so stored hashes still verify; a version 2 projection adds `identity_version: 2`, `main_skill_group` and the support settings. `domain/migrate.py` upgrades a version 1 record to a new version 2 record with every support setting unknown and the main group the version 1 exporter used. Round trips compare at the source record's version.

Gems now resolve on the (`gemId`, `variantId`) pair, which is how PoB identifies a gem variant.

Real PoB output showed more state the record does not hold. The import audit now reports each as a blocking loss when it differs from what PoB writes by default: gem `count`, global effect toggles, skill part, stage, mine and minion choices, stat set, corruption, per-effect gem children, `includeInFullDPS`, `groupCount`, item- or passive-granted groups with changed settings, `useSecondWeaponSet`, activated flask and charm slots, selected runes, alternate unique variants, a secondary ascendancy, mastery effects, non-empty custom config modifier text and unknown config elements. Calcs-tab selections are reported without blocking (CalcsTab.lua reads them for its own view, not the main output).

Groups PoB generates itself (`source="Default Attack"`, `Tree:<node>`, `Explode`, `Thorns`) are no longer imported as ordinary groups. PoB rebuilds them on load from the gear and tree the record holds; importing them created duplicates on reload. A changed setting on one, or a main skill inside one, is a blocking loss. The engine lane confirms group counts, main skill and every numeric output are unchanged for all twelve fixtures.

The importer no longer copies non-blocking losses into `unresolved_refs`; before, a clean import with any reported metadata exported as incomplete.

### Build variants (P02 follow-up, P04-T01)

`evaluation/variants.py` splits one document into variants: the document's active selection, plus every loadout linked by PoB's own rule (`buildMode:SyncLoadouts`: `{id}` title links, exact titles, single-set tabs). Each variant gets its own BuildSpec with a `variant_id` naming its sets, the shared raw blob and the shared source document. A set no variant uses is reported, never merged; a title naming two sets in a tab forms no variant. One deviation from PoB is documented in the module: tree-version title prefixes are ignored.

### P04-T01 format dispatch and PoB parsing

`parsers/formats.py` picks the format from the bytes: PoB XML (root `PathOfBuilding2`), PoB code, item text, saved HTML, provider JSON. A declared format must agree with the bytes. Decoding reuses the P03 bounded checks. `parsers/pob.py` produces a `ParseResult` with issues (field path, locator, explanation), coverage counted by domain, and unknown elements and unrepresented values kept in `raw_extensions`. Missing tree, items or skills sections are unknown (partial), not empty. A missing `Build` element is `invalid` with `layout_unrecognized`. An unresolved class produces no BuildSpec. `pob2opt parse --source ID --corpus DIR --catalog DIR` stores the records in the corpus and reports a stored result on a second run.

### P04-T02 source parsers

D02 approves no provider representation, so the only build-data parser is the PoB one (local files and sharing codes). Mobalytics, Maxroll and poe.ninja pages and JSON get `provider_parser_blocked` and no build; a saved page still yields its visible prose as unverified claims. The required fixture categories are covered for the PoB representation: complete build, missing gear, multiple variants, old tree version, unknown entity, layout change and absent popularity. Per-provider parsers stay blocked on D02.

### P04-T03 entity resolution

`parsers/resolve.py`: `naming_from_catalog` builds the PoB naming tables from catalog entities, native keys first; a PoB value claimed by two entities is left out of the table and reported. `resolve_name` is exact name or alias within one table and locale, with ambiguous candidates returned and no fuzzy match. `migrate_build` makes a new record against another catalog, recording renames and removals and never substituting. Item affix lines are matched against the catalog's prefix/suffix rows by text, rolled value inside the tier range and spawn weight on the base's tags; the result is reported as coverage and issues, not written into the items, because PoB item text cannot carry catalog modifier IDs. Unique, implicit, enchant, rune and crafted lines are not in that table and are not checked. A name without stats is a template claim.

### P04-T04 claims

`parsers/claims.py` extracts one unverified `MechanicClaim` per sentence that names a catalog entity exactly (gems, skills, classes, ascendancies, item bases, notable and keystone passives), with a locator holding character offsets so the passage can be retrieved. A gem and the skill it grants are one subject; any other repeated name is ambiguous and left out. `ClaimIndex` is SQLite FTS5 (LIKE fallback) over headings and claim text with entity and patch filters; user text is quoted. Conflicts are found by a fixed rule (same subjects and patch, same sentence once numbers and negations are abstracted) and kept side by side.

### P04-T05 dedup and audit

`parsers/corpus.py`: exact duplicates grouped by gameplay hash with every creator kept; identical copies count once as evidence. Family labels are engineer proposals from a fixed rule (main skill plus its supports and triggered skills); only an accepted review yields a family ID. Holdout splits never divide a family. `audit_variant` re-reads the source document independently of the importer and compares allocations, gear modifier lines, skill and support settings and set bindings.
