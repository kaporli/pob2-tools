## Implemented behavior

Input: a `BuildSpec`, the `PatchProfile` whose rules decide it, and
optionally the `GameCatalog` the profile pins, the `ItemInstance` records for
the equipped items, and the state the pinned engine holds after loading the
build's own document.

Previously there was nothing. No code anywhere decided whether a build was
legal; `EvaluationResult.legality` existed as a field with no producer, and
`architecture.md`'s `legality_unknown` error code had no caller.

Now `LegalityValidator.validate(build, profile)` returns a `LegalityReport`
with three separate things: **violations** (a rule in the profile is broken),
**unknowns** (the rule or the input needed to decide is missing, each citing
the `DataGap` that says what to collect) and **constraints** (the derived
point and resource numbers, each with what it was measured against or `None`).

### Eighteen declared checks, and what a verdict rests on

`report.DECLARED_CHECKS` lists them: class membership, ascendancy membership,
character level, passive point budget, ascendancy point budget, passive
connectivity, passive choices, socketed entities, equipment slots, equipment
hands, item requirements, item construction, skill restrictions, support
restrictions, gem levels, reservation resources, weapon-set rules and
post-import verification.

The overall verdict is `illegal` if anything was violated, `unknown` if
anything could not be decided, and `legal` only when **every one** of the
eighteen answered `legal`. A check that did not run is `unknown`, not `legal`.
That is the mechanism that makes the acceptance criterion true rather than
promised: attribute and Spirit results are two checks out of eighteen, the
report says so in a note, and passing them cannot produce a verdict.

### What is undecidable on the profile this engine produces

P02-T02 exported all 113 `SlotRule`s with an empty `accepted_base_categories`
and a **blocking** gap. Equipment legality therefore cannot be decided from
this profile, and the validator returns `unknown` for it and cites
`gap/p02-t02/slot-accepted-base-categories`. It does not read the category off
the item's name, its display name or its rarity. The code path that *would*
check a category exists and runs when a rule carries one; it is not reachable
from any profile this engine can export today, which is exactly what the gap
says. The consequence is worth stating plainly: **on this profile, a build
with any equipment at all cannot be `legal`**. The best available answer is
`unknown` with the gap attached.

Five more answers are `unknown` against a P02-T02 gap rather than guessed:

| Question | Answer | Gap cited |
|---|---|---|
| More passives than levelling grants | `unknown`, because quest rewards add an unknown number | `gap/p02-t02/quest-passive-point-rewards` |
| Ascendancy points inside the maximum | `unknown`, because no rule says when each is earned | `gap/p02-t02/ascendancy-point-unlock-schedule` |
| Weapon-set points inside the total | `unknown`, because no rule says when each is earned | `gap/p02-t02/weapon-set-point-unlock-levels` |
| A gem above its natural maximum level | `unknown`, because items grant levels past it | `gap/p02-t02/gem-level-legality` |
| A skill entry with no gem | `unknown`, because the profile has no skill level limit | `gap/p02-t02/skill-level-limit` |

The validator raises fourteen gaps of its own, declared once each in
`legality/gaps.py` with the measurement that would close them. The load-bearing
ones: `unverified-import` (the build was never loaded into the engine),
`character-attribute-totals` and `reservation-measurement` (nothing here
recomputes an engine quantity), `theoretical-item-construction` (no
item-generation rules exist, so a constructed item's constructability is
undecidable and cannot be accepted), `attribute-choice-options` (the exported
node rows carry neither `isAttribute` nor the option list upstream has), and
`catalog-not-supplied`. `ReportBuilder.unknown` refuses an unknown that cites
no gap, so an undecidable check cannot quietly become a shrug.

### What is decided, and against what

Everything else comes from the profile's own rule records, never from a
literal. The level range, the point maximums, the support limit, the class to
ascendancy map, the slot table and the weapon-set shape are read from
`CharacterRules`; where a rule is absent the check says so and cites a gap
rather than defaulting. Sourced decisions include: a class or ascendancy the
rules do not carry; an ascendancy belonging to another class; a level outside
the range; more ordinary passives than the sourced maximum of 99; more
ascendancy points than the sourced maximum of 8; more weapon-set points than
the sourced total of 24; an allocation with no path to the class start node
through other allocated nodes; ascendancy nodes from two ascendancies at once;
a choice on an unallocated node; a jewel socketed into a node the catalog
reports as something other than a socket; a slot the profile does not declare;
one item or one listing filling two slots; a hand bound to a slot belonging to
no weapon set or to a different one; more hands than the set has; an item
whose level requirement the character does not meet; an item whose attribute
requirement a *measured* total does not meet; an item record whose parse status
is invalid; more sockets than the catalog's base allows; a support gem used as
an active skill and an active gem used as a support; more supports in one group
than the profile's limit; a gem below level 1; a reservation the engine reports
as exceeding its pool; and a skill granted by an item the build does not wear.

Two of those deserve a note. The support limit is the engine's declared one,
and P02-T02's own rule record says upstream warns above it and still
calculates; the violation message repeats that rather than claiming the game
rejects a sixth support. And a *duplicate* support is `unknown`, not a
violation: the profile carries a count and nothing about repetition.

When the build's own `progression` declares a normal or ascendancy point
budget, that budget is used and the check becomes decidable. The constraint
records that the basis was the build's declaration and not the catalog.

### Verified after the import, because a clean import proves nothing

`legality_state` is one new read-only handler in `bootstrap.lua`, appended
immediately before the dispatch section. It reports what the engine holds
after a load: every allocated node id split into tree and ascendancy, the
engine's own point counts, the item in each slot with its base and its
requirements, the socket groups and their gems, and the calculated pools and
attributes. It allocates nothing, equips nothing and does not recalculate, and
an engine test shows a legality read between two evaluations changes no
primitive value and forces no reload.

With that state, allocation and equipment are read from the engine rather than
from the record, the point counts are the engine's own (which exclude the
class start node), and the record's claims are *checked* against the engine:
a different level, class, allocation or equipment is a violation. Nothing is
corrected. Without that state the `post_import_verification` check is
`unknown`, so a record-only validation can never return `legal`.

The claim this exists for is demonstrated on the real engine: the sample build
wearing a base that requires level 79, at level 29, **imports without a
complaint**, the engine equips it and calculates it, and the validator returns
`illegal` naming the level requirement.

## Adverse cases

Exercised:

* each of the eighteen checks failing on its own, and six failing at once;
* a build that imports cleanly into PoB and is illegal anyway;
* a record whose level, allocation and equipment its own document does not
  produce: three violations, no correction;
* no catalog supplied at all: every catalog-dependent check is `unknown` with
  the `catalog-not-supplied` gap, and nothing resolves by default;
* a catalog the profile does not pin, a build resolved against another
  catalog, and an imported state belonging to another build: all three are
  refused with a `ValueError` naming the mismatch, because validating against
  the wrong data is a coordinator defect and not a build problem;
* an equipped item with no supplied record, an item whose parse status is
  invalid, an item with unresolved modifiers, and an item with no provenance;
* a node id, gem id or item base the catalog does not carry: `unknown` with
  the unresolved-entity gap, never illegal, because the catalog can be
  incomplete;
* an engine state whose allocated node keys are not numeric;
* a gap raised twice in one report: one record, with every reference it hit
  named in its explanation;
* the same build validated twice: identical reports.

Not tested:

* **no gameplay evidence exists for any rule here, and none is claimed.**
  Every decision traces to a rule P02-T02 read out of Path of Building, which
  is a model of the game and not the game;
* a profile whose slot rules *do* carry base categories. That branch is
  written and unreachable from any export this engine can produce, so it is
  covered only by the invented-world lane's absence of categories, not by a
  positive case. Closing the slot gap is the thing that would test it;
* two-handed weapon and off-hand conflicts, which the same gap covers. Nothing
  here knows which bases occupy both hands;
* the ascendancy connectivity walk is exercised on the invented tree and on
  the real tree only for a build with no ascendancy. The sample build has
  none, so no real ascendancy allocation was walked;
* `item_modifiers` and trade hashes are untouched: item construction asks only
  whether an item is sourced and whether its modifiers resolved;
* performance. The connectivity walk is a breadth-first search over the
  exported edges and was not measured against a full 99-point allocation on a
  5000-node tree in a loop, which is what P08 will do with it.

## Deviations and unresolved questions

1. **`ADAPTER_VERSION` moved from `p02-t02.0` to `p02-t03.0`.** Its docstring
   says to bump it whenever the adapter changes what it asks the engine for,
   and it can now ask for the legality state. The primitive path is unchanged
   and no stored evaluation exists to invalidate. The cost is that a
   `PatchProfile` exported before this change is now refused by
   `_check_profile`, which is the behaviour P02-T02 introduced deliberately;
   the committed `catalog-export.json` records the old string and is evidence
   about that export, not a live profile. If the reviewer wants P02 to land
   with one version bump, this and P02-T04's should be reconciled at
   integration rather than here.
2. **`pob2opt.evaluation` was never in `pyproject.toml`'s package list.**
   P02-T01 added the package and did not ship it; an installed wheel has no
   engine boundary at all. The tests import the working tree, so nothing
   caught it. This change adds `pob2opt.evaluation` and
   `pob2opt.evaluation.legality`. It is a fix to someone else's omission
   inside a file three other P02 branches may also touch; it is two lines.
3. **`legality` is a subpackage of `evaluation` and is not imported by
   `evaluation/__init__.py`.** It reads the catalog (for entity ids and the
   tree), and `pob2opt.catalog` imports `pob2opt.evaluation.protocol`.
   Importing it from the package surface would make that cycle real. Callers
   import `pob2opt.evaluation.legality`. The alternative was to duplicate the
   entity-id scheme, which contracts.md's "do not create alternative schemas"
   rules out.
4. **A gap's `subject_ids` are the build and the profile, not the entities it
   could not resolve.** contracts.md requires every cross-record reference to
   resolve, and the identifiers an unresolved-entity gap is about are exactly
   the ones that do not. They are named in the explanation as text and carried
   as fields on the report's findings. If the reviewer prefers the gap to
   carry them structurally, that needs a `DataGap` field that is explicitly
   not a reference, which is a schema change and a decision record.
5. **Exceeding the support limit is reported as a violation.** The profile
   carries `max_supports: 5` as a rule, and P02-T02's own description says
   upstream only warns. Treating a declared limit as a rule is the reading
   this task is built on; the violation message repeats the caveat. The
   alternative reading, that a sixth support is `unknown`, is a one-line
   change. This is a game-rule interpretation and the reviewer should confirm
   it.
6. **A duplicate support is `unknown` rather than illegal**, for the opposite
   reason: the profile carries no rule about repetition, so there is nothing
   to violate.
7. **An unresolved catalog reference is `unknown`, not illegal.** A node, gem
   or base the catalog does not carry may be missing from the catalog rather
   than from the game. This follows P02-T02's `resolve.py`, which reports an
