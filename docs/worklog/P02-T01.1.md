# P02-T01.1 native engine reliability

The memory growth is reproduced, localized to live data inside PoB, and
contained by bounding workers. It is not fixed: the PoB statement that keeps
the data alive is not identified, and PoB is not patched. Evidence and
commands: [docs/evidence/P02-T01.1](../evidence/P02-T01.1/README.md).

## Cause, as far as it is established

- Reproduced on clean `origin/main` without instrumentation: two of three
  full engine runs grew past 4 GB in about 35 s in the F11 module.
- A bounded repeat of that module's sequence in one in-process engine stops
  in 35 of 106 children, always in the sixth to eighth iteration. It is
  intermittent for identical inputs and happens with the JIT off.
- The engine keeps running normally while memory grows. A full collection
  frees little: the growth is live. About 1 M `ModList` objects are reachable
  from PoB's shared passive-tree cache (`build.latestTree.nodes`, mainly the
  class variants of switchable nodes), which survives `new_build`.
- Not established: the exact retaining statement and the source of the
  intermittency.

## Containment

`EngineAdapter` (one engine per worker process) now bounds each worker:

- **Hard limit** `memory_limit_bytes`, default 3 GiB. Sampled every 0.1 s
  while waiting for a reply, including startup. Above it the worker is killed
  and the request raises `EngineMemoryLimit`, an `EngineCrash` stored as
  `engine_crash`, carrying the limit and observed bytes.
- **Soft limits** `recycle_after_bytes` (default 2 GiB) and
  `max_requests_per_worker` (default off). A worker past either finishes its
  request, then is replaced before the next public operation. Never inside
  one: a `primitives` call's load and read always use the same process.
  Counted in `recycles`, not `replacements`.
- **No unlimited replacement.** After `max_consecutive_failures` (default 3)
  workers in a row are lost to a crash, timeout or memory limit, the adapter
  raises `EngineReplacementExhausted` instead of starting another. Only a
  completed public operation resets the count. There are still no retries:
  a failed request stays failed.
- `worker_history` records each ended worker: pid, requests, peak sampled
  memory and why it ended.
- Memory is private bytes on Windows and resident bytes on Linux. On other
  platforms a bound is refused with `EngineUnsupported`; pass `None` to run
  unbounded explicitly.
- `restart_worker` now counts one replacement, not two.

The in-process test session (`tests/conftest.py`) cannot replace its engine,
so it exits with code 87 above `POB2_TEST_MEMORY_LIMIT_MB` (default 3072),
naming the running test, instead of growing until the machine stops it.

## Verification

- Offline: 1,486 passed, 1 existing xfail (unit and integration), including
  nine new synthetic-worker cases: kill at the hard limit, recycle after the
  soft limit, no recycle inside an evaluation, request budget, loss cap and
  its reset, probe refusal, bounded defaults. Every replacement result equals
  a never-limited worker's.
- Real engine, four new cases with bounds a real worker always crosses: a
  64 MB limit tripping at startup, the loss cap, memory and request-budget
  recycling. Results match a fresh unbounded worker within the P02-T01
  tolerance.
- Real-engine soak, 300 evaluations each: 300 of 300 matched at
  2048/1280 MB (five memory recycles) and at the defaults (no recycle; the
  worker settles at about 1.39 GB).
- Every engine module in its own pytest process: 12 modules, 156 passed,
  peak 879 MB (`docs/evidence/P02-T01.1/runs/permodule-*`). Run as one
  session, the same suite stopped in the F11 module in four of five runs
  (two on `origin/main`, two on this branch).
- Python 3.10 lane: the new and existing adapter unit tests pass (62).

## Not done

- The runaway never occurred through the adapter in 600 soak evaluations, so
  no real runaway has been killed by the hard limit; that path is tested with
  a synthetic runaway and a startup limit.
- The engine test suite still uses one in-process engine. In one session it
  still fails most runs in the F11 module; the guard turns that into exit 87
  rather than fixing it. Moving engine tests onto bounded workers, or running
  modules in separate processes in CI, is a follow-up.
- `pob2-mcp`'s server keeps one in-process engine and is not bounded.
- Instrumented runs showed native access violations that no uninstrumented
  run reproduced; recorded, not explained.
- The four-hour soak remains P08-T05.
