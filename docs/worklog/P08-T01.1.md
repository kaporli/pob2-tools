# P08-T01.1 objective contract handoff

This delivery implements the D07 request/objective/aggregate contracts. It does
not implement prepare, combat evaluation, ranking or search. PR #11 carries
the code; PR #12 carries the stacked spec 1.1 update.

## Review repairs

The initial review is retained in [P08-T01.1](../reviews/P08-T01.1.md).

- R1: the objective registry identifies the required native Flicker gem and
  active-effect keys. Scope resolution requires unique catalog rows, matching
  raw native IDs, the gem's `grantedEffectId` link, and explicit non-support
  flags. Selecting either representation still requires evidence for both.
  Other skills, support gems, mixed selections, missing rows and ambiguous or
  inconsistent mappings produce scope issues. Names are suggestions only.
- R2: reference-checked aggregate writes resolve their manifest from the store
  or the pending batch and enforce objective ID/version/hash binding before
  any rows are written. Stored validation repeats the check. Explicit staging
  remains available, but staged conflicts make bundles unreadable and surface
  their field errors through `IncompleteBundle`.
- The required skill mapping participates in objective identity. This changes
  the unmerged v2 objective hashes from the original PR head; regenerate any
  development v2 manifests/aggregates rather than reusing those hashes. V1
  records, hashes, and successful bundle-check output retain their meaning.

The native keys match the pinned PoB `ce566eac45ea8a86477f513c7ee65a1ebe60014e`
`src/Data/Gems.lua` entry for `Metadata/Items/Gems/SkillGemFlickerStrike`, which
links to `FlickerStrikePlayer`. The exported fields are defined by
`pob2mcp/bootstrap.lua`'s `catalog_gems` and `catalog_granted_skills` handlers.
The resolver verifies those fields in the supplied catalog; a registered key
alone does not approve a patch, class scope or gameplay mechanic.

the scope resolver, hash the benchmark and attribution content, and freeze
